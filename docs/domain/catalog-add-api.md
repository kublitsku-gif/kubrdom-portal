# Заведение товаров снаружи (`POST /api/catalog/add`)

- Единственная ручка ЗАПИСИ, открытая наружу (`src/catalog.js`, смонтирована в `worker.js` до авторизации). Умеет ровно одно: дописать карточку в «Базу · материалы» (`expProducts`). Ни правки, ни удаления, ни других разделов снимка.
- Секрет **`CATALOG_TOKEN`** свой, схема `Authorization: Bearer`. Панельный `ADMIN_TOKEN` сюда не пускают намеренно: он пишет снимок целиком разделами, и серверной проверки прав по `work_id` у записи нет — отдать его ради каталога значит отдать вместе с ним договора, финансы и команду. Тот же довод, что у `MCP_TOKEN`. Не задан секрет — эндпоинта нет (404, fail-closed). Задаётся руками (`wrangler secret put CATALOG_TOKEN --name kubrdom-portal-api`), деплои его не трогают.
- Тело: `{items:[{name, cost, unit|mode, store, url, packName, packBase, packPer, sheetM2, lenPer, shopPer}]}`, до 100 товаров за раз. `unit` — обычное слово из таблицы («м.п.», «рулон»), режим карточки выводится из него.
- **Тёзка не заводится и НЕ правится** (`planAdd`, сравнение по `nameKey`): по имени идёт связь сметы с товаром, и вторая карточка с тем же именем означала бы, что цену правят в одной, а считают по другой. В ответе `{added, skipped}` — по каждому пропуску сказано, почему.
- **Форма карточки общая с панелью** (`normProduct`): `productNew` в `admin.js` зовёт её же, и словарь единиц (`UNIT_WORDS` / `PACK_AS_WORD`) тоже живёт здесь. Вторая копия разошлась бы с первой, и «рулон» из таблицы стал бы штукой в одной из дверей заведения товара.
- Пишем через `writeSection` (сторож `updated_at`), и **если заводить нечего — не пишем вовсе**: холостая запись подняла бы версию снимка, и каждая открытая панель потянула бы мегабайт ради нуля изменений.
- Заведение попадает в «🕘 Историю» (`logEvent`, автор `api`): запись снаружи обязана быть видна там же, где правки людей.
