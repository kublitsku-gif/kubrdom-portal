# Права, синхронизация и восстановление данных

## Серверные границы

`src/access.js` — общие права и проекция снимка. Бригадир/рабочий видит назначенные объекты (в `user.objs` или в `contractDocs[].responsible`), свои чеки и выплаты. При сохранении сервер подмешивает скрытые записи из базы: отсутствие чужого объекта в снимке не удаляет его. Изменение чужих ID и запрещённых разделов возвращает 403, без частичной записи. Администратор управляет пользователями/ролями/настройками, финансист — финансовыми разделами. Дорогие внешние операции проверяют соответствующие права.

Права персональной сессии перечитываются из D1 на каждом запросе; удаление/отключение пользователя и смена PIN отзывают сессию. При записи права повторно сверяются с тем же снимком, версии которого участвуют в транзакции. Исторические токены без `sv` требуют нового входа после обновления. Чтение файлов R2 по уже известной ссылке остаётся публичным по действующей архитектуре.

## Подтверждение и версии

`src/state-schema.js` проверяет известные разделы, массивы/словари, идентификаторы, дубликаты, глубину и размер (1 900 000 байт на раздел, 12 МиБ на запрос). Неизвестные поля внутри записей сохраняются для совместимости. Перед выкладкой CI проверяет текущий снимок D1 этим же валидатором; данные и секреты в журнал не выводятся.

`POST /api/state/admin_panel` принимает только изменившиеся разделы с `baseVersions` для каждого. Старый клиент без версий получает 428. Администратор может явно отправить `force:true`; обычные сотрудники — нет. `src/state-store.js` проверяет версии и пишет все разделы одной транзакцией D1: неуспех CHECK в `state_write_guard` откатывает весь batch. Новая версия строго больше старой даже при совпадении миллисекунд. Для персональных сессий проверяются также версии прав/назначений.

Ответ содержит `accepted`, `versions` и канонические `items` — панель подтверждает только перечисленные разделы. Правки, сделанные во время запроса, остаются несохранёнными и отправляются следующим запросом.

## Слияние и локальные копии

`src/panel-sync.js` содержит контроллер сохранения, поллинга и конфликтов; `src/sync-state.js` — чистое трёхстороннее слияние (исходная версия, локальная, серверная). Независимые поля объединяются; одновременное изменение одного поля или удаление/правка требует выбора человека. Закрытие уведомления не продвигает исходную версию. «Обновить» также проходит через слияние.

`src/snapshot-cache.js` хранит снимок, исходную версию, версии разделов и признак неподтверждённой записи. Ключ раздельный для сотрудника и вкладки; новая вкладка может восстановить последний неподтверждённый черновик того же сотрудника. Локальное подтверждение выдаётся после успешного localStorage или завершения транзакции IndexedDB. Если оба хранилища отказали, интерфейс предупреждает о невозможности сохранить копию. PIN и хеши в копии не сохраняются. Новые правки не должны заменять исходную подтверждённую версию.

## Проверки

`test-state-api`, `test-access-security`, `test-login-guard` используют настоящую SQLite через стандартный Python, включая rollback. `test-sync-safety` связывает две панели с настоящим Worker и SQLite. Для проверки браузерного IndexedDB: `npm run build`, затем `node tools/serve-safety.mjs` и `/checks` на локальном порту 8790. Стенд использует только синтетические данные и локальные тестовые учётные записи. `/admin` показывает настоящий собранный интерфейс.
