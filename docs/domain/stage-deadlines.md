# Сроки по этапам

- План живёт НА ЭТАПЕ объекта: `s.planStart` / `s.planEnd` (обе необязательные). Дедлайн договора говорит про сдачу целиком и загорается, когда всё уже сорвано; этап — то, чем стройка меряется на площадке.
- **Факт не храним** — выводим из следов работы (`timeLogs`, `doneAt`) в `stageFact`. Отдельное поле пришлось бы вести руками, и оно разошлось бы с работами при первой правке. Конец этапа показываем, только когда закрыты ВСЕ работы: иначе «закончен такого-то» читается как сдача.
- Логика — в `src/stages.js`, общая с напоминаниями (как `src/supply.js` для закупок). В `admin.js` только показ: плашка в шапке этапа, строка худшего этапа на карточке в списке. Не дублировать расчёт в панели — чат и экран разойдутся.
- Состояния: `overdue` (план кончился, этап открыт), `notStarted` (пора было начать, следов нет), `soon` (≤2 рабочих дней), `go`, `lateDone`, `done`, `none`. Счёт в РАБОЧИХ днях, как у дедлайнов.
- В Telegram уходят только `overdue` / `notStarted` / `soon` (`stagesNeedingAttention`, утренний крон): рассылка про идущие в сроке этапы — спам, из-за которого бота мьютят.
- План правится в карточке объекта в режиме правки (`obj-stage-plan`), запись по `change`, а не по `input`: нативный date-инпут шлёт input на каждую цифру года, и перерисовка выбивала бы календарь из-под пальца.
- Дату-строку `YYYY-MM-DD` собираем только `isoLocal()` из `src/dates.js`, а «сегодня» — `todayISO()` оттуда же. `toISOString().slice(0,10)` на дате, построенной локальным календарём, уводит результат на день назад в поясах восточнее Гринвича. Исключение — осознанный «день по Москве» (`Date.now() + 3ч`, `mskToday()`): там пояс браузера ни при чём, рабочий день у компании считается по МСК.
