# Приёмка этапа и график платежей

- Транш живёт в договоре: `c.tranches = [{id, title, amount, stageId, paidAt, paidBy}]`. Привязка к ЭТАПУ — суть механизма: клиент принимает этап, и сумма становится «к оплате». Это единственное место, где «сделано» встречается с «оплачено».
- Приёмка живёт на этапе объекта: `s.acceptance = {askedAt, askedBy, acceptedAt}`. Запрос приёмки — отдельное действие производства, а не автоматика по «все работы закрыты»: закрытая галочка иногда стоит раньше фактической готовности.
- **Отметку о приёмке ставит СЕРВЕР** (`POST /api/client/accept-stage`), потому что `postState` для клиента read-only — его частичный срез затёр бы базу. Ручка проверяет по токену, что этап принадлежит объекту ЕГО договора, и пишет через `writeSection` с проверкой `updated_at` (между чтением и записью панель могла сохранить объекты).
- После приёмки Worker заводит обычный вопрос `kind:"money"` финансисту с суммой транша — так у «выставить счёт» сразу есть адресат, возраст, эскалация и Telegram. Повторную приёмку и повторный вопрос сторожит фиксированный id `iss_acc_<stageId>`.
- Оплату транша отмечает руками тот, кто ведёт кассу. Автоматически по приходам не угадываем: один платёж закрывает то один транш, то половину другого, а ошибка здесь — неверный счёт клиенту.
- В «Финансах» принятые, но не оплаченные этапы висят блоком «К оплате»: этих денег не видно ни в приходах (ещё не пришли), ни в P&L (он про план).
