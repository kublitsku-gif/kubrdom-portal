# CRM отдельным приложением (/crm): лента Авито и пуши

- **Адрес `/crm` — та же панель (тот же `admin.js`), открытая в режиме «только CRM».** `dist/crm.html` НЕ лежит в `public/`: его собирает `tools/stamp-admin.mjs` из `admin.html`, подменяя манифест (`/crm.webmanifest`), заголовок, цвет темы и apple-иконку. Править вёрстку оболочки — только в `admin.html`, иначе два файла разъедутся. Скрипт в `crm.html` идёт абсолютным путём (`/admin.<hash>.js`).
- Режим включает `isCrmApp()` → `isCrmPath(location.pathname)` (`src/crm-app.js`): `/crm`, `/crm/`, `/crm.html`. В `page()` при этом: вкладка принудительно `crm`, ленты вкладок и «Ещё» нет, внизу своя панель `crmAppBarHtml()` («🎯 Воронка / 💬 Чаты»). Без права на CRM — `crmNoAccessHtml()`, а не чужая вкладка.
- Манифест `crm.webmanifest`: `id` и `start_url` = `/crm?app=1`, `scope:"/crm"`, свои иконки `kubrdom-crm-*.png` (логотип + синий значок чата справа сверху). У портала `id:"/admin"`, `scope:"/admin"`.
- **Области двух приложений не должны пересекаться.** Пока у портала был `scope:"/"`, его WebAPK перехватывал и `/crm` — CRM открывалась внутри иконки портала. Сторожит `test-crm-app` («/crm вне области портала»). Уже установленный WebAPK портала узнаёт новую область только при обновлении; ускорить: Chrome → `chrome://webapks` → «Update КубрДом — Портал управления» → запустить портал и закрыть его из недавних (обновление ставится через Play за минуту).
- **Как поставить CRM на Android, если на телефоне уже есть иконка портала:** меню Chrome «⋮ → Установить и создать ярлык» на том же сайте пишет «Это приложение уже установлено» (меню смотрит на сайт целиком) — им CRM не поставить, а «Создать ярлык» даёт лишь ярлык во вкладке Chrome. Рабочий путь — кнопка страницы: экран входа `/crm` → «Установить приложение» → тёмная кнопка «Установить приложение» (`pwa-install`, событие `beforeinstallprompt`) → системное окно «КубрДом CRM» → «Установить». Проверено на POCO F7 Pro 28.10.2026: получилась отдельная иконка «CRM КубрДом» (WebAPK с путём `/crm`).
- **Лента «Чаты»** — `crmView="chats"` (`tCRMChats`), диалог — `crmView="chat"` + `crmChatKey` (`tCRMChat`). Данные — те же `crmChats` из `/api/ai/chats`, порядок и признаки считает `chatFeed`. Ответ уходит тем же `crm-send-avito` (`data-cid="chat"` → поле `crm-reply-chat`). В полном портале в ленту ведёт кнопка «💬 Чаты» в шапке воронки.
- **«Не отвечено» = последняя НЕ-черновая реплика от клиента.** Черновик ИИ клиенту не ушёл и ответом не считается — так считают и `chatFeed`, и `chatUnanswered` (бейдж вкладки). Не расходить.
- Реплики пузырями рисует одна функция `crmMsgsHtml` — и в карточке клиента, и в диалоге. **Черновик ИИ — не пузырь ответа**: вид задаёт `draftKinds` (`src/crm-app.js`). `pending` (последний черновик, после него клиенту ничего не ушло) — жёлтая карточка «🤖 ИИ ПРЕДЛАГАЕТ ОТВЕТ · НЕ ОТПРАВЛЕНО» (+ «🟠 нужно одобрение»), в диалоге с кнопками «📤 Отправить как есть» (`crm-draft-send`, с `confirm`, шлёт тем же `/api/ai/send`) и «✏️ Править» (`crm-draft-use`, кладёт текст в поле). `stale` — бледная строка, `used` (ушёл потом тем же текстом) — не рисуется, `failed` — ваш ответ из CRM, который Авито не принял (сервер хранит его `status:"draft", manual:true`), — красный пузырь «Не ушло клиенту».
- **Повторы вебхука Авито.** Авито шлёт вебхук заново, пока мы не ответили 200, а `avitoWebhook` ждёт ИИ (десятки секунд) — раньше каждый повтор ложился новой репликой клиента со своим черновиком, пушем и сообщением в Telegram (29.10.2026: «пришлю ТЗ» ×4 за полчаса). Теперь входящее хранит `avitoMsgId` (`payload.value.id`), и `aiProcessIncoming` по `hasIncoming` молча пропускает уже записанное. Старые повторы (без id) прячет экран: `dupHidden` — тот же текст клиента подряд без нашего ответа между ними → видна одна реплика и последний черновик; тем же фильтром чистится история для ИИ. Реплики с разными id — настоящие и видны обе.
- **Переписка = то, что в Авито.** В диалоге видны только реплики клиента, наши отправленные ответы, одна свежая карточка ИИ (`pending`) и красные «не ушло»; старые неотправленные черновики (`stale`) не рисуются. Наши сообщения, набранные прямо в Авито, приходят тем же вебхуком (автор = `AVITO_USER_ID`) → `aiRecordOutgoing` дописывает их как «🙋 Вы» (`fromAvito`), а эхо наших же ответов из CRM/бота узнаёт по `avitoMsgId` (его пишут все места, где зовётся `avitoSend`) или, у старых, по тексту за 10 минут.
- **Сверка с Авито** — `mergeAvitoHistory(local, avitoHistory(GET messenger/v3/.../messages))`: повторы выкидываются, реплика Авито узнаётся по id или по тексту той же стороны (ей ставится id), недостающее вставляется по времени. Своё НЕ удаляется никогда — если Авито не ответил, только уборка повторов. Зовётся при открытии диалога (`crmSyncChat` → `POST /api/ai/resync`, раз за вкладку) и разово по всем диалогам (`crmCleanupOnce` из `crmTick`, по 3 за проход, отметки — строка `crm_marks/cleanup2`, `__all` = прошли все). Где история Авито получена, наша реплика без пары в Авито за тот же период уходит (повтор, удалённое, другой формат текста — версия Авито уже вставлена); старше истории — остаётся. Наше из истории, чего у нас не было, подписано «🙋 Вы» (`manual`, `fromAvito`). Авито на части диалогов отвечает 402 — там только уборка повторов. Повтором считается тот же текст клиента в любом месте после нашего последнего ответа: клиент прислал два сообщения — Авито повторяет пару (А, Б, А, Б).
- **Чистка Telegram** — очередь `crm_marks/tgq` (`{ops,i,log,done}`), собрана `dupTelegram` по бэкапу диалогов ДО сверки (после сверки id черновиков-повторов уже нет) и положена в D1 руками; `crmTgQueue` проходит её после сверки, ≤30 вызовов за крон. Черновики-повторы удаляются по `tgMsgId`, посты «👤 Клиент» (их id не хранили) ищутся на 1–4 id ниже следующего черновика и удаляются, только если текст совпал (пересылка в ту же ветку без звука → чтение → удаление копии). Ответ Telegram на каждую операцию — в `log`. **Бесплатный Worker даёт ~50 внешних запросов за запуск крона** — первый проход (cleanup1) чистил Telegram вместе со сверкой и упёрся в лимит («Too many subrequests»).
- **Кнопки черновика в Telegram ищут черновик по своему сообщению** (`draftForButton` по `tgMsgId`), а номер из `callback_data` — лишь запасной путь. После сверки номера реплик сдвигаются, и старая кнопка «✅ Отправить» иначе ушла бы клиенту с чужой репликой; уже отправленный черновик повторно не шлётся («Черновик уже неактуален»).
- Карточка, открытая из диалога (`crm-chat-card`), по «назад» возвращается в диалог (`crmBackView`).

## Работа с диалогом (29.10.2026)

Чистая логика — `src/crm-app.js`, экран — раздел «CRM КАК ОТДЕЛЬНОЕ ПРИЛОЖЕНИЕ» в `admin.js`, сервер — блок «CRM-приложение» в `worker.js` (маршруты `CRM_CHAT_ROUTES`, все `/api/ai/*` → право crm/marketing).

- **Лента**: `filterFeed` — режимы `FEED_MODES` (все / ждут ответа / с черновиком / архив), стадия, поиск (имя, телефон, объявление, весь текст; цифры телефона ищутся без форматирования). Поиск фильтрует строки в DOM (`crmFeedApplySearch`), без перерисовки — иначе на телефоне прыгает клавиатура. Состояние ленты экранное → `ui()`.
- **Таймер «ждёт»** — `waitSince`: первая реплика клиента после нашего последнего ОТПРАВЛЕННОГО ответа. С `WAIT_ALERT_MIN` (15 мин) строка красная.
- **Архив / спам** — `c.archived` / `c.spam` в `aiChats` (`POST /api/ai/chat-flag`), в ленте свайп влево или «⋯». Новое сообщение клиента снимает архив (`aiProcessIncoming`); спам — сообщение сохраняется, но без пуша, Telegram и ИИ.
- **Чаты `u2u` — без объявления.** Ключ `avito:u2u-…` — клиент написал в профиль, а не из объявления (`u2i-…`); Авито объявления у такого чата не отдаёт, поэтому в ленте и в диалоге вместо него «💬 написал в профиль» (`isDirectChat`).
- **Имя в ленте** — `feedName`: имя карточки, если это не заглушка (`isPlaceholderName`: «Новый клиент», «Avito · 123», «Пользователь»…), иначе имя из Авито; `crmAutoLinkAvito` заодно переименовывает такую карточку.
- **Объявление в шапке** — `c.item` из `GET messenger/v2/.../chats/{id}` (`avitoChatMeta` → `avitoChatInfo`): при первом сообщении, у старых диалогов — при открытии (`POST /api/ai/chat-info`, один раз). Заодно имя «Avito · 123» меняется на имя клиента из Авито. Ссылка объявления — только на avito.ru.
- **Фото**: вебхук принимает `type:"image"` (`avitoImageUrl` — самый крупный размер), реплика `{text:"📷 Фото", image}`; ИИ на фото не отвечает (ждём человека), в Telegram — `sendPhoto`. Отправка: «📷 Фото» → сжатие → `POST /api/file` (R2 `plans/<uuid>`) → `POST /api/ai/send-photo` (только такие ключи); «🖼 Планировка» → `POST /api/ai/send-plan` (ключи `PLAN_IMAGES`). Картинки в `src` — только через `safeImageUrl` (https или свои `/api/file`, `/plans`).
- **Каталог PDF**: выбран вариант «Место, куда хочется возвращаться», 8 страниц, цены на 03.11.2026. `src/crm-catalogs.js` задаёт название и ссылку R2. В Telegram документ прикрепляется к ответу, в Авито доступно скачивание PDF для приложения (подробнее ниже). «Посмотреть PDF» открывает исходный файл. Файл хранится в R2 `catalogs/dom-dlya-zhizni-20261103.pdf`, исходник — `assets/crm-catalogs/`; Pages job загружает его до публикации панели. Новое издание — новый ключ, потому что `/api/file` кэшируется как immutable. Тест: `test-crm-catalogs`.
- Шаг загрузки каталога фиксирует `wranglerVersion: '3.90.0'`: у `r2 object put` этой версии нет флага `--remote`, запись удалённая по умолчанию (локальная только с `--local`). Не переносить флаг из локального Wrangler 4 в CI без проверки версии.
- Telegram: «Прикрепить каталог PDF» выбирает документ для ответа; отправка через `sendDocument` с `business_connection_id`, текст - подпись (до 1024 символов). Можно отправить один PDF без текста. Выбор привязан к конкретному чату/полю ответа, при ошибке остаётся. В истории хранится ссылка на файл, не base64. В Авито подтверждённого метода PDF-вложения в этой интеграции пока нет, сервер не подменяет запрос файла ссылкой.
- **«🔄 ИИ» у черновика** — `POST /api/ai/redraft {clientKey, idx, hint}`: история до черновика + указание менеджера → новый текст в ТОТ ЖЕ черновик (`rewritten`). Своё указание можно надиктовать: 🎤 рядом с полем — общая диктовка браузера `voiceDictate` (Web Speech API, ru-RU, без сервера; та же, что в песочнице нейропродавца). Текст ложится в поле и сам не отправляется; пока идёт диктовка, фоновый опрос чатов экран не перерисовывает.
- **Быстрые ответы** — `quickReplies(settings)`: `settings.crmQuickReplies` (общие для всех, правятся «⚙»), иначе `QUICK_REPLIES_DEFAULT`. Тап добавляет текст в поле, не шлёт.
- **Телефон**: номер из переписки (`extractPhoneFromChat`) — кнопки «📞» и «WhatsApp / Telegram / Max» в шапке диалога (те же ссылки, что в карточке клиента: `wa.me/7…`, `t.me/+7…`, `max.ru/7…`) и сам ложится в привязанную карточку без телефона (`crmAutoLinkAvito`).
- **Напоминания** — `c.remindAt` (мс) + `c.remindNote` в карточке клиента; список «📅 Сегодня» (`todayReminders`) над воронкой и лентой.
- **Крон `*/5` → `crmTick`**: пуш «⏰ Ждёт ответа N мин» (`waitReminders`: ≥15 мин и <суток, по Москве 8–22, один раз на реплику) и «📞 Напоминание» (`dueReminders`, ссылка `/crm?go=client%3D<id>`). Что уже напомнили — строка `work_states` `crm_marks/push`, НЕ `aiChats`: её пишет вебхук, и запись крона затёрла бы свежее сообщение.
- **Сводка** (`crmView="summary"`, вкладка «📊» внизу) — `salesSummary`: лиды за 7 дней к прошлой неделе (по `c.date`), медиана времени ответа и доля ответов за 15 мин (30 дней, черновики не в счёт), «дошли до стадии» (сейчас на ней или дальше — истории переходов нет), объявления → диалоги / встречи / договоры.

## Пуши

- **Scope service worker — `/crm`** (`CRM_SW_SCOPE`), не `/`: Chrome на Android показывает пуш от имени WebAPK CRM (scope `/crm`) и ставит отметку на ЕГО иконку, только если воркер внутри области приложения; со scope `/` уведомление шло от Chrome (`pkg=com.android.chrome`), мимо иконки CRM. Старую подписку с регистрации `/` `crmPushMoveScope` переносит молча (подписка на новой, отписка и снятие старой). На Android ещё нужно разрешение уведомлений самому Chrome (`POST_NOTIFICATIONS`) — без него пуши не показываются вовсе (так было на POCO 29.10.2026).
- `public/sw.js` — service worker **только для пушей, без обработчика fetch** (сеть и свежесть `admin.js` как раньше; не добавлять кэш). Регистрирует его лишь приложение `/crm` (`crmAppInit` из `_startLoops`).
- Кнопка «🔔 Включить уведомления» (в ленте, только в `/crm`) → `Notification.requestPermission` → `GET /api/push/key` → `pushManager.subscribe` → `POST /api/push/subscribe`. «Проверить» — `POST /api/push/test` (только свои подписки), «Выкл» — `POST /api/push/unsubscribe`.
- Подписки — `work_states` с `storage_key="push_subs"`, строка на телефон (`work_id` = хэш адреса). В снимок панели не попадают (читаются только `admin_panel` + `STATE_SECTIONS`), версию снимка не двигают.
- **Шлём пуш в `aiProcessIncoming` сразу после записи входящего Авито-сообщения**, до ИИ: по нажатию диалог уже есть. Получатели — подписки тех, у кого СЕЙЧАС есть доступ к CRM (`pushAllowUid`: admin / `crm` / `marketing`, не `disabled`); подписка переживает увольнение, поэтому права проверяются при отправке. 404/410 от push-сервиса — подписка удаляется.
- Адрес подписки принимается только у настоящих push-сервисов (`cleanSubscription`: FCM, Mozilla, Windows, Apple), иначе Worker можно было бы заставить постучаться куда угодно.
- Шифрование и VAPID — свои, на WebCrypto (`src/webpush.js`, RFC 8291 aes128gcm + RFC 8292). Ключи: `VAPID_PUBLIC_KEY` в `wrangler.toml`, приватный — GitHub-секрет `VAPID_PRIVATE_KEY` → `deploy.yml` → Worker. Сменить ключи = все телефоны должны заново включить уведомления.
- Нажатие на пуш: окно `/crm` открыто — `postMessage({type:"crm-open"})` → `crmOpenFromUrl`; нет — открывается `/crm?go=chat%3D<key>`, разбирает `applyDeepLink` (`q.chat`).
- **Цифра на иконке** — `unansweredCount` (диалоги Авито, где последним писал клиент; черновик ИИ не ответ; архив/спам не в счёт). Открытая CRM ставит её сама (`crmAppBadge` → `navigator.setAppBadge`), закрытая — из пуша: в данных пуша `count`, `sw.js` зовёт `setAppBadge`/`clearAppBadge`. Работает у УСТАНОВЛЕННОГО приложения (WebAPK на Android, установленное PWA на Маке); окно `--app` из обёртки «CRM КубрДом.app» своей иконки и цифры не имеет. Ответили, пока приложение закрыто, — цифра обновится при следующем пуше или открытии (тихих пушей Chrome не даёт).
- **Цифра на ярлыке в Доке Мака** — ярлык «CRM КубрДом.app» (AppleScript, не PWA) висит в фоне и раз в минуту спрашивает `GET /api/crm/badge?k=<ключ>` → `{count}` (`unansweredCount`), ставит её на свою иконку (`dockTile.badgeLabel`). Маршрут до общей авторизации; ключ — случайный, в D1 только его SHA-256 (`work_states crm_marks/badge_keys`, `{hashes:[…]}`), отдаётся одно число. Клик по ярлыку при открытом ярлыке открывает окно CRM (`on reopen`).
- Android-пуши идут через FCM (Google). Если в РФ отвалится — дублировать в Telegram (sales-бот уже шлёт ветку по каждому клиенту).
- Сторожит `tools/test-crm-app.mjs` (в т.ч. расшифровка пуша «браузером» по RFC и проверка подписи VAPID).

## Черновики после входящего (03.11.2026)

- `src/ai-drafts.js`: в режиме без автоотправки входящее сразу запускает подготовку. Пропущенный черновик восстанавливается при открытии/опросе активного чата (`POST /api/ai/prepare`) и резервным кроном раз в 5 минут (один свежий диалог Авито за проход). Сам импорт истории по-прежнему ничего не отправляет клиенту.
- Подготовка получает общий lease на входящую реплику в `aiChats.draftState`. Запись через `commitState` с версией: параллельные правки и другие чаты сохраняются; если клиент написал ещё или менеджер уже ответил, устаревший результат отбрасывается. Уже существующий черновик не заменяется. При ошибке видны сообщение и «Повторить», при подготовке - её состояние.
- Под черновиком сразу видны «Короче», «Теплее»; «ИИ» открывает остальные варианты и своё указание. Обновление сохраняет набранный текст ответа. Поле `draftState` принадлежит Worker, в снимок панели не пишется.
- `POST /api/ai/draft-mode` (только администратор) включает подготовку и выключает автоотправку, меняя лишь `settings.aiEnabled/aiAutoSend` со стражем версии. Workflow `Check Avito delivery` умеет включить этот режим, подготовить выбранный чат и проверить доработку, не отправляя ответ клиенту и не печатая его текст в CI.
- Проверки: `test-ai-drafts`, `test-crm-app`, `test-scheduled-dispatch`, `test-sales-dialog`.

- Обращение по имени по умолчанию: `aiSellerReply` получает `clientName` из диалога для подготовки, доработки и последующих ответов. Профиль передаётся как данные; ИИ выделяет имя, `src/client-name.js` проверяет его принадлежность профилю и добавляет обращение, если модель пропустила. Первый ответ — «Здравствуйте, Янина!», доработка сохраняет имя. Технические имена/ники и неясные профили не используются в приветствии; имя не выдумывается. Сторожи `test-client-name`, `test-ai-drafts`.

- PDF в Авито: CRM предлагает скачать сам PDF для прикрепления внутри приложения Авито. Кнопка не вставляет ссылку и не помечает документ доставленным. На POCO с установленным com.avito.android проверка `query-activities SEND application/pdf -p com.avito.android` вернула No activities found: системное «Поделиться» не открывает прикрепление PDF в Авито. Публичный метод отправки PDF пока не подтверждён. Telegram отправляет документ через `sendDocument` из CRM.

## Отказы Авито при отправке (04.11.2026)

- Доступный список чатов и работающий webhook не доказывают доступ к переписке: история конкретного чата вернула HTTP 402 с сообщением «Перейдите на подписку с API мессенджера, чтобы получить доступ к чатам». Это ограничение на стороне Авито; проверять подписку нужного профиля, не менять ключи вслепую.
- `avitoSend` проверяет HTTP-статус и подтверждённый `id`; ответ с ошибкой даже при наличии `id` не считается доставкой. При 402 менеджер видит пояснение о подписке и возможность ответить в самом Авито. `aiSend` сохраняет `deliveryError` у неотправленного ответа, `crmMsgsHtml` выводит её с экранированием. Старые ошибки без этого поля не переименовываются задним числом.
- Workflow `Check Avito delivery`, `diagnose_name`: читает метаданные/историю и статусы CRM, не отправляет клиенту сообщение. Проверка текста использует только заведомо несуществующего получателя. Тексты переписок и секреты в логи не выводить. Сторожи: `test-avito-delivery`, `test-crm-app`.

## Работа со сделками (29.10.2026)

- `src/crm-sales.js` — общие правила, `src/crm-sales-ui.js` — блоки карточки и отчётов. Сохранение через существующие версии разделов; миграция D1 не требуется.
- `changeClient` добавляет события в `history` при смене стадии, ответственного, результата, задачи и версии КП. Старая история переходов не выдумывается. Отчёт за 30/90/365 дней считает реальные достижения стадий выбранной группой заявок; прямой переход к договору не засчитывает встречу.
- Следующее действие: `remindAt/remindNote`, совместимые поля Telegram `salesFollowupAt/salesNote`, штампы `actionUpdatedAt/statusUpdatedAt`. `sales-workspace` сверяет их с последними синхронизированными штампами; выполненная задача не воскресает из Telegram. Перенос открывает форму без удаления прежней задачи.
- `ownerId/ownerName` — ответственный; пуш задачи адресуется ему. Без ответственного действует общий список получателей CRM. Рабочие фильтры показывают клиентов без действия, без менеджера и с просрочкой. Результаты сделки используют статусы Telegram; отказ требует причины, отложенная сделка — даты следующего действия.
- `brief` содержит product/size/budget/region/equipment. `proposals` хранит версии КП: ссылку https, сумму, комплектацию и подтверждённую менеджером дату отправки. Файлы в снимок не вставляются.
- Объединение по совпадающему нормализованному телефону сохраняет исходную карточку с `mergedInto`, объединяет историю, КП, планировки и массивы `avitoKeys/tgKeys`. `chatKeys` учитывает оба канала и одиночные старые поля. Скрытые карточки исключаются из CRM и CardDAV; ближайшая задача переносится в основную карточку. Связанные договоры отображаются через `mergedIds`.
- Рекламные расходы — `settings.crmAdCosts`, вводит администратор; группировка по `campaign` или источнику. Неуказанный расход отображается прочерком. Сумма подписанных/завершённых основных договоров — не денежные поступления.
- `POST /api/ai/brief` использует настроенного ИИ-провайдера и только диалоги, привязанные к клиенту (Авито и Telegram). Возвращает предложение, не пишет стейт и не отправляет клиенту сообщений. Менеджер проверяет поля; заполненный бриф не перезаписывается, дата задачи задаётся отдельно.
- Проверки: `test-crm-sales`, `test-crm-sales-api`, `test-tg-business`, `test-sales-workspace`.

- По умолчанию рабочий фильтр — «Все». Верхние счётчики и воронка считают всех необъединённых клиентов независимо от рабочего фильтра; фильтр меняет только список. Нажатие стадии сбрасывает рабочий фильтр на «Все», иначе «Договор» показывал пустоту при активном «В работе». Страхует `test-crm-sales`.
