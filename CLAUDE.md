# Портал КубрДом

Портал строительной компании (бани и дома из контейнеров): CRM, объекты, сметы, договоры, снабжение, табель рабочих. Язык проекта и общения — русский.

Прод: **https://portal.kubrdom.ru** (свой домен обязателен: `*.pages.dev` / `*.workers.dev` в РФ режутся по SNI). Админ-панель: `/admin`.

## Архитектура

- **Cloudflare Pages** `kubrdom-portal` — фронт React/Vite (src/ → dist/) + **standalone админ-панель** `public/admin.html` + `public/admin.js` (~700 КБ vanilla JS — основной код панели).
- **Worker** `kubrdom-portal-api` (`src/worker.js`) + **D1** `banya-db` + **R2** `kubrdom-files` (фото/документы) + Telegram-зеркало фото/видео (бот, супергруппа с темами по объектам).
- `functions/api/[[path]].js` (Pages Function) проксирует `/api/*` → Worker на стороне edge — это обход блокировки workers.dev в РФ, НЕ ломать. Клиент ходит same-origin (`API_BASE=""`), файловые URL относительные (`/api/file/<key>`).
- Панель синхронизируется снимком всего стейта в D1 (`storage_key=admin_panel`), автосейв + live-опрос; авторизация заголовком `X-Admin-Token` (секрет `ADMIN_TOKEN` на Worker, fail-closed).
- **Сейв шлёт ТОЛЬКО изменившиеся разделы** (`dirtySections`). Не возвращать «шлём весь снимок»: сторож `base` на сервере проверяет ровно те `work_id`, что пишутся, поэтому запись всех разделов подряд означала 409 всем остальным на любую чужую правку. Форс-сохранение («Сохранить как есть») — исключение, оно шлёт всё и без `base`.
- Эталон стража (`updateServerCounts(items, onlyKeys)`) после такого сейва двигается только по отправленным разделам: по остальным сервер ничего не подтверждал, и записать туда локальный счёт значит обезоружить стража там, где вкладка устарела.
- **Опрос чужих правок спрашивает только версию** — `GET /api/state/:key/version` отдаёт `max(updated_at)`, и полный снимок (~1 МБ) тянется лишь когда версия выросла. Не возвращать опрос к «каждые 15 с тянем всё»: это мегабайт четыре раза в минуту на телефон бригадира. Если версия не пришла (старый Worker в окне деплоя отдаёт 404) — клиент сам падает на полный опрос.

## Деплой

- **Автодеплой: пуш в `main` → GitHub Actions** (Pages + Worker, секрет `CLOUDFLARE_API_TOKEN` комплексный). Ручной wrangler не нужен.
- **Commit-сообщения — ASCII-чистые**: кириллица/грязные байты роняют Pages-деплой (`Invalid commit message [8000111]`).
- Новый секрет в deploy.yml: СНАЧАЛА `gh secret set <NAME>` (хоть плейсхолдером), ПОТОМ пушить код со ссылкой — иначе job падает.
- После `git push` не брать `gh run list --limit 1` сразу (поймаешь предыдущий прогон) — матчить run по `headSha`.
- Секрет `TG_BOT_TOKEN` задан вручную на Worker и переживает деплои — CI его не трогает.

## Сборка админ-панели (не ломать!)

- `npm run build` = `vite build` + `build:admin` (esbuild `public/admin.js` → `dist/admin.js`, target **es2017**).
- `admin.js` — ВНЕШНИЙ файл. НЕ инлайнить обратно в admin.html: >700 КБ инлайн-скрипта мобильный Safari не тянет (белый экран).
- target es2017: `?.`/spread транспилируются, но `async/await` остаётся НАТИВНЫМ. Не опускать target ниже — regenerator-полифил вешал iOS.
- Проверка после деплоя: в задеплоенном admin.js `?.` = **0 вхождений**. Размер — ориентир, а не константа: он растёт с кодом (на 2026-08-28 ~1650 КБ). Сверять надо порядок величины, а не точное число.
- Кириллицу esbuild экранирует в `\uXXXX` с ЗАГЛАВНЫМИ hex, поэтому `grep "Можно делать"` по задеплоенному бандлу **ничего не найдёт**. Проверять деплой по ASCII-маркерам (`data-a`-именам, id, классам).
- `<meta viewport>` содержит `maximum-scale=1` (лечит авто-зум iOS на инпутах) — не убирать.

## Критичные правила данных

- **Лимит D1: строка ≤ 2 МБ.** Снимок сохраняется одним транзакционным batch — одна раздутая строка откатывает ВСЁ сохранение. Поэтому файлы (фото, PDF, договоры) ВСЕГДА в R2 ссылками, НИКОГДА не base64 в стейт.
- Загрузка файлов: клиент жмёт фото до ≤1 МБ, Worker принимает img+pdf+office до 20 МБ по allowlist расширений (SVG/HTML запрещены — XSS).
- Частые микро-обновления UI — через `rerenderTab()` (частичная перерисовка `#tab-content`), не полный `render()` (дёргает скролл на iOS).
- Паспортные данные шаблона договора живут ТОЛЬКО в localStorage (`kubr_ctTpl`), в снимок D1 не попадают — так и оставить.

## Сроки по этапам

- План живёт НА ЭТАПЕ объекта: `s.planStart` / `s.planEnd` (обе необязательные). Дедлайн договора говорит про сдачу целиком и загорается, когда всё уже сорвано; этап — то, чем стройка меряется на площадке.
- **Факт не храним** — выводим из следов работы (`timeLogs`, `doneAt`) в `stageFact`. Отдельное поле пришлось бы вести руками, и оно разошлось бы с работами при первой правке. Конец этапа показываем, только когда закрыты ВСЕ работы: иначе «закончен такого-то» читается как сдача.
- Логика — в `src/stages.js`, общая с напоминаниями (как `src/supply.js` для закупок). В `admin.js` только показ: плашка в шапке этапа, строка худшего этапа на карточке в списке. Не дублировать расчёт в панели — чат и экран разойдутся.
- Состояния: `overdue` (план кончился, этап открыт), `notStarted` (пора было начать, следов нет), `soon` (≤2 рабочих дней), `go`, `lateDone`, `done`, `none`. Счёт в РАБОЧИХ днях, как у дедлайнов.
- В Telegram уходят только `overdue` / `notStarted` / `soon` (`stagesNeedingAttention`, утренний крон): рассылка про идущие в сроке этапы — спам, из-за которого бота мьютят.
- План правится в карточке объекта в режиме правки (`obj-stage-plan`), запись по `change`, а не по `input`: нативный date-инпут шлёт input на каждую цифру года, и перерисовка выбивала бы календарь из-под пальца.

## Ревизии шаблона: «в шаблоне изменилось»

- Объект — глубокая копия шаблона (`reidStages`), и отличаться он ОБЯЗАН: он живёт своей сметой. Поэтому дифф «объект против шаблона» бессмыслен, нужен третий участник — слепок шаблона на момент создания объекта (`o.tplBase`, пишется в `add-obj`). Дальше это обычное трёхстороннее сравнение, как при слиянии снимков.
- Храним не содержимое, а короткие подписи работ (`workSig`, FNV-хэш от имени, цены и материалов): полный слепок сорока работ весил бы десятки килобайт в КАЖДОМ объекте, а раздел `objects` и так ближе всех к лимиту строки D1.
- Ключ сопоставления между копиями — `estId`: `reidStages` выдаёт новые id, а `estId` копирование переживает. Работы без `estId` (докупка снабженца, ручные) не сравниваются вовсе.
- `safe:true` — объект свою копию не трогал, принять можно молча. Правка с двух сторон помечается спорной, и решает человек.
- Принятие переносит ТОЛЬКО план (имя, цену, материалы). `id` работы, часы, фото и отметку «выполнено» сохраняем — иначе принятая правка обнуляет бригаде день работы. Материалы получают свои `id`: общий id «протёк» бы отметками закупки между объектами.
- «Ничего не принимать» просто сдвигает слепок. Без этого отклонённая правка всплывает в каждом рендере, и баннер становится фоном, который не читают.

## Приёмка этапа и график платежей

- Транш живёт в договоре: `c.tranches = [{id, title, amount, stageId, paidAt, paidBy}]`. Привязка к ЭТАПУ — суть механизма: клиент принимает этап, и сумма становится «к оплате». Это единственное место, где «сделано» встречается с «оплачено».
- Приёмка живёт на этапе объекта: `s.acceptance = {askedAt, askedBy, acceptedAt}`. Запрос приёмки — отдельное действие производства, а не автоматика по «все работы закрыты»: закрытая галочка иногда стоит раньше фактической готовности.
- **Отметку о приёмке ставит СЕРВЕР** (`POST /api/client/accept-stage`), потому что `postState` для клиента read-only — его частичный срез затёр бы базу. Ручка проверяет по токену, что этап принадлежит объекту ЕГО договора, и пишет через `writeSection` с проверкой `updated_at` (между чтением и записью панель могла сохранить объекты).
- После приёмки Worker заводит обычный вопрос `kind:"money"` финансисту с суммой транша — так у «выставить счёт» сразу есть адресат, возраст, эскалация и Telegram. Повторную приёмку и повторный вопрос сторожит фиксированный id `iss_acc_<stageId>`.
- Оплату транша отмечает руками тот, кто ведёт кассу. Автоматически по приходам не угадываем: один платёж закрывает то один транш, то половину другого, а ошибка здесь — неверный счёт клиенту.
- В «Финансах» принятые, но не оплаченные этапы висят блоком «К оплате»: этих денег не видно ни в приходах (ещё не пришли), ни в P&L (он про план).

## Материалы: каталог → смета → шаблон → объект → закупка

- **`m.pid` — ссылка позиции на карточку каталога** (`expProducts`). Имя/цена/магазин остаются КОПИЕЙ: объект живёт своей сметой и не переписывается при правке базы. Раньше связь рвалась в `_tplEstWork` (материал становился снимком по имени), и «где используется» собрать было не из чего. Совпадение по имени связью не считать: имена правят и дублируют.
- Исторические позиции привязывает `ensureMatPids()` при загрузке — только при ТОЧНОМ совпадении имени и когда в каталоге такой товар один. Тёзки остаются без `pid`: привязка к чужой карточке потом меняла бы не тот товар.
- Карточка товара показывает «Где используется» (шаблоны, объекты, работы) и расхождение цены. **Синхронизация цены — только вручную и с выбором области** (`matApplyCatalogPrice`): цена в объекте — согласованный бюджет, а не витрина.
- **`w.cost` работы = материалы + `w.labor`** (`workTotal`): цена бригаде за работу назначается человеком и к сумме материалов отношения не имеет, но материалы в работе всё равно есть и в её стоимость входят. Меняете цену или количество материала — пересчитывайте `w.cost` тут же; `normalizeWorkCosts()` чинит это лишь при следующей загрузке.
- Исключение — работа **«под ключ»** (`w.costAll`): её `cost` это фиксированная цифра из договора с бригадой, материалы в неё уже включены, и пересчёт её НЕ трогает. Без флага `normalizeWorkCosts()` при каждой загрузке возвращал бы `cost` к сумме материалов и молча стирал согласованную цену.
- Замена товара снимает отметки закупки (`supplyClearMarks`) и **отвязывает** позицию партии (`needId=null`), а не удаляет её: деньги реально потрачены и должны остаться в сумме партии. Правка цены заменой НЕ считается — отметки сохраняются.
- Объединённая строка закупки (`_mergeMats`) правится целиком: имя/цена/магазин на все потребности, количество у каждой своё. Строка слепляет позиции по УСЕЧЁННОМУ имени (`normMatName`: «ОСП 30 м²» и «ОСП 18 м²» → одна «ОСП»), поэтому в модалке показываются собственные имена — иначе замена молча переименует обе фасовки.

## Склад остатков

- Раздел снимка `stock` — то, что физически осталось и ждёт следующей стройки: `[{id, pid, n, mode, cost, store, qty, srcObjId, srcObjName, at, by}]`. Одинаковые позиции складываются в одну строку, нулевая строка удаляется.
- Кандидат в остаток — **перекуп** (`needOverBought`: куплено больше, чем требует смета). Это единственная величина, которую портал знает точно: фактический расход на объекте никто не считает.
- Сопоставление остатка с потребностью — по `pid`, имя только запасной путь для позиций без ссылки. «ОСП 30 м²» и «ОСП 18 м²» — разные фасовки, молча считать их одним товаром нельзя.
- `stockCoverNeeds` берёт по каждой потребности ровно нехватку, а не «сколько есть»: иначе на объект уезжает лишнее и там снова копится остаток.
- Выдача создаёт партию с `fromStock:true`. Такая партия **в кассу не проводится** — деньги за этот материал ушли раньше, на прошлом объекте, и второй расход был бы двойным счётом. Она же исключена из счётчика «не проведено», иначе финансист видит долг, который нечем закрыть. Приёмку не подделываем: материал ещё надо довезти, мастер отмечает её как обычно.

## Заявка на замену материала

- Замена по ходу стройки — это деньги: снабженец видит разницу со сметой ДО сохранения, а разница от `settings.matChangeLimit` (по умолчанию 10 000 ₽) уходит заявкой тому, кто отвечает за деньги. Порог правится прямо в модалке теми, кто согласовывает.
- Заявка — обычный вопрос по объекту с `kind:"matchg"` (`matChangeRequest`), поэтому у неё сразу есть адресат, возраст, эскалация и Telegram. Сама правка лежит в `t.mat`, применяется кнопкой «✅ Применить замену» ТЕМ ЖЕ кодом, что и прямое сохранение (`matChangeApply`) — иначе «согласовано» и «сделано» разъедутся.
- `payer:"client"` при подорожании заводит строку в `extraWorksPlan` договора: иначе замена молча становится убытком компании. `payer:"company"` — не заводит.
- Пока заявка открыта, позиция в снабжении помечена «⏳ замена на согласовании» (`matPendingChange`): без этого уходит вторая такая же заявка, а бригадир не понимает, почему материал прежний.
- Вид `matchg` помечен `auto:true` и в форме «новый вопрос» не показывается: без payload'а такая заявка бессмысленна.

## Позиции «выбор клиента»

- `m.sel` — позицию выбирает клиент (плитка, печь, двери, сантехника), и сумма в смете становится **бюджетом выбора** (`matSelBudget`). `m.selDue` — до какого числа, `m.selDone` — когда выбор состоялся.
- Правило вместо порога: дешевле или вровень с бюджетом — замена идёт без бумаг; **дороже — согласование всегда**, каким бы ни был `matChangeLimit`. Это уже не наша экономия, а счёт клиенту, и решать за него снабженец не может.
- В форме замены у такой позиции по умолчанию стоит «за счёт клиента» — видимый выбор, а не подмена при отправке. Применённая замена ставит `selDone`, но `sel` НЕ снимает: по метке видно, чья это была позиция и сколько закладывали.
- Предикат общий (`pendingSelections` в `src/supply.js`): по нему рисует плашки панель, показывает список кабинет клиента и шлёт утреннее напоминание крон — «просрочен» на экране и в чате обязан совпадать. Напоминание уходит сопровождению и руководству, не бригаде: разговаривать с клиентом — их работа.
- Клиенту показываем бюджет словом «заложено», а не «доплатите»: иначе выбор превращается в спор постфактум.

## Спецификация дома: продажа собирает объект

- Продавец собирает дом клиенту из планировки: помещение → отделка помещения. Раздел снимка `specSheets`, вкладка «🏠 Спецификация» (доступ у РОП и менеджера по продажам). Расчёт — в `src/spec.js`, общий модуль: одни и те же числа нужны экрану, печатной форме клиенту, сумме договора и составу работ объекта. Разъедься они — клиент получит одну цену на руки и другую в договоре.
- Вариант выбора — это ПОМЕЧЕННАЯ смета: `optScope` (`room` / `global` / пусто = входит всегда), `optGroup` («Стены»), `optLabel` («МДФ»), `optSurface` (`floor`/`wall`/`ceil` — чем меряется). Отдельной сущности «опция» нет: смета уже знает свои материалы, а вторая копия того же разошлась бы с первой.
- Выбор по комнате хранится **по группе**: `sheet.rooms[roomId][group] = estId`. Не по трём поверхностям — «Стены черновые» и «Стены чистовые» это разные решения об одной стене, в трёх ячейках они бы столкнулись.
- **Раскладка** (`SPEC_POINTS`, `r.pts`) — то, что дизайн-проект рисует значками, а бригада монтирует поштучно: окна, двери, розетки (обычные / влагозащищённые / уличные), выключатели, светильники, споты, тёплый пол, кондиционер, вытяжка, радиатор. Считается ПО ПОМЕЩЕНИЯМ, потому что там же и монтируется, а клиент читает проект по комнатам («в зале шесть розеток и шесть светильников»). Нулевые ключи не храним.
- Смета с `optPoint` берёт количество из раскладки: «Розетка — монтаж» ×15 умножает и материалы, и цену. `optPoint` ортогонален `optScope`: обязательная позиция считается по всему дому, комнатная — по своей комнате. Точек нет — позиции нет: платить за монтаж того, чего не заложили, не за что. Площадь у такой позиции не считается — штуки и квадраты не смешиваем.
- Площади считаются из размеров помещения (`roomArea`): пол = ш × д, потолок равен полу (это одна плоскость, а не отдельный размер), стены = периметр × высота. Количество материала под площадь — `matQtyForArea`: м² как есть, листы и пачки через `packPer` вверх, штучное не трогаем (саморезы от площади не считают).
- Чертёж планировки можно **загрузить прямо в спецификацию** (`obj-doc-upload` → `specs.planUrl`), а размеры внести руками тем же редактором, что у планировок и объектов (`specsEditorHtml`, владелец через `specOwner`). Планировок в базе нет под каждый вид и под каждого клиента — чертёж приносят на встречу. Кнопка «В базу» заводит загруженный план в `dbPlans` копией размеров: иначе он грузится заново каждому клиенту.
- Планировку выбирают **плитками с миниатюрой чертежа** (`specPlanTiles`), не селектом: имена у планировок дежурные («Планировка», два одинаковых «Дом + спальня»), и свою только что загруженную в списке имён не узнать. Показываются ВСЕ, своя категория первой: видов смет уже шесть (апартаменты, глэмпинг…), а категорий у планировок две, и жёсткий фильтр оставлял продавца с пустым списком.
- **Спецификация — КОПИЯ планировки, а не ссылка** (`specApplyPlan`). Планировку в базе правят постоянно, а проданное обязано остаться таким, как продали. Смена планировки сбрасывает выбор по комнатам: `id` помещений стали другими, и выбор повис бы в пустоте.
- Наценка ОДНА на спецификацию (`sheet.markup`, по умолчанию `settings.specMarkup`), не по работам, как в КП: продавец должен понимать, что он назвал клиенту, а не собирать сумму из сорока процентов. В печатной форме наценка размазывается по позициям пропорционально, иначе суммы по помещениям не сойдутся с итогом.
- Клиенту печатаем позиции **по ЭТАПАМ** с подытогом каждого: стройка меряется этапами, по ним же идут сроки, приёмка и транши, и предложение должно читаться в том же разрезе. Сводка по помещениям идёт отдельной короткой таблицей в конце — в разрезе этапов она повторяла бы одни и те же комнаты в каждом блоке.
- В каждой позиции печатаем **состав материалов** (название и количество с единицей) — это и есть спецификация, а не КП. Закупочных цен и себестоимости там нет: количество клиенту нужно, наша калькуляция — нет. Формулировка состава одна на экран и на печать (`specMatsText`): разойдись они, в кабинете обещали бы одно, а на бумаге стояло другое.
- `sheetIssues` перечисляет, чего не хватает (нет планировки, не задана высота, не выбран вариант), и продавец видит это ДО клиента. Отказ от предупреждения останавливает создание договора — иначе предупреждение просто текст.
- **Объект создаётся из спецификации, а не из шаблона** (`specBuildStages`): `o.templateId=""`, `o.specId`, работы той же формы, что даёт `_tplEstWork`, поэтому закупка, приёмка, сроки и ревизии работают без единой правки. Раньше объект копировался из фиксированного шаблона, и всё, что клиент выбрал при продаже, до стройки не доезжало.
- **Одна спецификация — четыре захода** (`specView`): `sheet` — список со свёрнутыми блоками, `plan` — комнаты тапом по плану, `matrix` — таблица «помещение × группа», `steps` — мастер из четырёх шагов. Все пишут в ОДНО место (`sh.rooms[roomId][group]`, `sh.global[group]`), поэтому цена не зависит от способа показа. Новая спецификация открывается мастером, дальше продавец живёт в списке: правка одной комнаты не должна требовать путешествия по шагам.
- Четыре способа задать геометрию (модель, планировка из базы, чертёж файлом, размеры руками) свёрнуты в ОДНУ строку «откуда дом» с переключателем внутри. Раньше все четыре висели на экране одновременно и все пустые — первый экран занят выбором, которого продавец не понимает.
- На кнопке варианта — **разница в цене** (`optionCost` из `src/spec.js`), а не полная сумма: клиенту важно, во сколько обойдётся замена. Считает это общий модуль, а не панель: кнопка обязана обещать ровно ту сумму, которая встанет в итог и в договор.
- «Не хватает» — не текст, а **кнопки** (`specGaps` → `spec-jump`): тап раскрывает нужный блок, подсвечивает пропуск и скроллит к нему. Предупреждение, которое никуда не ведёт, читают один раз, а потом оно становится фоном.
- Цена приклеена к низу экрана (`specBarHtml`), себестоимость и наценка спрятаны за «👁 для своих»: этот экран разворачивают к клиенту.
- **Комплектация** (`settings.specPresets = [{id,kind,name,note,rooms:{group:estId},global:{group:estId}}]`) собирает дом целиком одним тапом. Это ответ на главную боль продажи: цена появлялась только после двадцати выборов. Живёт в `settings`, а не отдельным разделом снимка — несколько десятков строк на всю компанию. Применение переписывает выбор во ВСЕХ помещениях, поэтому всегда спрашивает подтверждение, если есть что потерять (повторный тап по своей же комплектации — это сброс точечных замен). Комплектация — способ собрать, а не ссылка на состав: её удаление не меняет уже проданное.
- Договор из спецификации хранит `c.specId` и сумму `t.price` — через полгода видно, из чего эта сумма собралась. Если объект создан после договора, он привязывается к нему тут же: иначе договор остаётся без стройки, а стройка без денег.

## Модель контейнера

- Дом из контейнера — коробка фиксированного размера с перегородками и проёмами; больше в нём ничего нет, и этого хватает, чтобы считать площади, а из площадей — смету. Расчёт в `src/model.js`, в `admin.js` только показ и мышь.
- **Помещения хранятся ДЛИНАМИ, а не координатами границ** (`model.rooms[].len`): перетаскивание границы — это перенос миллиметров у соседа, и в таком виде сумма длин не может разъехаться с контейнером из-за округления. Соседа нельзя съесть меньше `MIN_ROOM`.
- `id` помещения переживает всё: деление, слияние, смену типоразмера. На нём висит раскладка и выбранная отделка — потеряй id, и выбор клиента слетит. При слиянии раскладка соседа складывается, а не пропадает: розетки всё равно монтировать.
- **Площади ЧИСТОВЫЕ** (`model.finish`, по умолчанию 76 мм на стену): обрешётка с утеплителем и обшивкой съедает сантиметров восемь, и счёт по железу контейнера давал лишний квадрат на комнату — это материалы и деньги. В проекте №7640467 контейнер 2352, помещения 2200.
- Модель — источник характеристик: `modelToSpecs` отдаёт те же `specs.rooms`, с которыми спецификация работала и раньше, поэтому отделка, раскладка, этапы и печать считаются без единой правки. Пока модель есть, ручной редактор размеров скрыт — два источника правды об одних помещениях разъедутся в первый же день.
- Проёмы (`model.openings`) стоят на стенах: длинные меряются по контейнеру, торцы — по ширине. **Межкомнатная дверь — проём на перегородке**: `side:"part"`, `after` — id отсека, СРАЗУ ЗА которым стоит перегородка (номер стены съезжает при делении и слиянии, id отсека — нет), плюс `into` (в какую сторону створка) и `hinge` (на каком откосе петли): угадать это нельзя, а нарисовать створку не в ту комнату — соврать. Дверь принадлежит двум комнатам сразу, и `openingRoom` отдаёт ОДНУ — ту, за которой стоит перегородка; иначе «монтаж двери» посчитается дважды и бригада закажет лишнюю. Поэтому дублировать её ещё и в `pts.door` нельзя: источник счёта один. Правится такая дверь во вкладке **«Перегородки»** списка проёмов (`MODEL_OP_SIDES`): сначала выбирается сама перегородка (их бывает несколько, и «добавить» обязано знать куда), дальше створка и петли переключаются кнопками, а положение — тем же ползунком и тем же жестом на плане, что у окон. На развёртке перегородок нет: развёртка — вид на стену коробки изнутри, поперечная стена в него не попадает, поэтому выбор её возвращает к плану. **Деление и слияние отсеков переименовывают перегородку** (она названа отсеком ПЕРЕД ней), поэтому `splitAt`/`splitRoom` переносят дверь на новый правый кусок, а `mergeRoom` убирает её вместе с исчезнувшей стеной — иначе проём молча уезжает в соседнюю комнату или висит на стене, которой нет. Сторожат `test-model.mjs` и `test-model-editor.mjs`. Проём знает своё помещение по координате и попадает в раскладку как `win`/`door`, поэтому «монтаж окна ×4» считается той же машинкой, что розетки. Стоимость самого изделия берётся из справочника `winTypes` — типовые окна и двери поставщика заводятся один раз. Двигают проём пальцем прямо на плане; тап без движения ничего не меняет, иначе прокрутка страницы переставляла бы окна. **Тап по готовому проёму выделяет его в ЛЮБОМ инструменте** (в «Убрать» — удаляет), и событие до холста не всплывает: ручки перетаскивания в режиме установки скрыты, и без этого поставленную дверь нечем было настроить — петли, сторона створки и положение числом живут у ВЫБРАННОГО проёма, а тап по ней инструментом «Двери» клал вторую поверх первой. Поставленный проём выделяется сразу — за петлями не надо переключать инструмент.
- **Каталог поставщика** (`WIN_CATALOG` в `src/model.js`) — изделия из спецификации ПК «Окна Столицы» ZZ/204764: система, размер, цена и **раскладка створок**. В справочник портала `winTypes` уезжает КОПИЯ (`winTypeFrom`, раскладка копируется вглубь): каталог правят, а проданное обязано остаться таким, как продали. Уже заведённое изделие каталог узнаёт по **виду и размеру** (`findWinLike`) и второй строкой не заводит — тот же заказ по двум ценам развести нельзя. Цена в каталоге за ОДНО изделие: в спецификации строка окна 500×500 стоит на две штуки. Межкомнатное полотно лежит там же с нулевой ценой (её ставит человек), и кнопка «завести полотно» в боевом редакторе теперь берёт его оттуда же.
- **Мини-картинка рисуется по раскладке изделия** (`winFace` + `winFaceSvg`), а не картинкой из PDF: два окна одного габарита, глухое и поворотно-откидное, стоят разных денег, а строка «1300×1150» их не различает. Последний ряд и последняя створка добирают остаток габарита — картинка обязана закрывать изделие целиком; что заданные числа и так сходятся, сторожит `test-win-catalog.mjs`. Изделие, заведённое руками, раскладки не знает — у него одна створка по виду, и это честно. Толщина линий — `vector-effect="non-scaling-stroke"`: в миллиметрах модели рама витража 2160×2390 на картинке в 40 px была бы ниткой. Показываются картинки только в опытном разделе — см. ниже.
- **Отсек делится и вдоль** (`bay.sub = {id, name, pts, at}`): санузел стоит в углу, а не во всю ширину. Дальше двух комнат в отсеке не идём — третья полоса в контейнере 2,35 м уже не помещение. Стена принадлежит той комнате, которая её касается: северная — первой, южная — второй. Отсеки с разным делением по ширине не сливаются: П-образную комнату модель описать не умеет, а врать про площади нельзя.
- **Развёртка стены** (`elevation`) — второй вид той же модели, то, чего план сверху показать не может: на какой высоте что стоит. Высоты точек лежат в каталоге (`SPEC_POINTS[].h`: розетка 300, выключатель 900, спот 1800, климат 2200), у проёма — в `op.sill`. Потолочный свет на развёртке не рисуем: высоты на стене у него нет. Точки разносятся по своей комнате равномерно — точных координат модель не хранит, и обещать их не надо.
- **Редактор на весь экран** (`modelFullOverlay`, `modelFull`) — оверлей `position:fixed`, а не растянутая вкладка: панель свёрстана в колонку 480 px под телефон, а планировку рисуют на большом экране. Инструменты: двигать / стена поперёк / стена вдоль / проём / убрать; окна и двери ставятся из справочника изделий. В режиме рисования ручки перетаскивания скрыты — иначе они перехватывают тап по стене.
- **Площади живут рядом с планом** (`modelAreasPanel`): двинул перегородку — увидел новые числа, ради этого редактор и открывают на весь экран. Там же правится всё, что есть в карточке: имя помещения, длина отсека числом, деление поперёк и вдоль, снятие перегородки — иначе за каждой цифрой надо выходить из полного экрана. На узком экране панель переносится под план.
- Стену ставят по одной, поэтому после неё инструмент возвращается в «Двигать»: в режиме рисования ручки скрыты, и человек решает, что двигать вообще нельзя. «Проём» остаётся включённым — окна ставят подряд.
- **В поле `type="number"` значение обязано быть с ТОЧКОЙ** (`numInp`): значение с запятой браузер считает невалидным и показывает поле ПУСТЫМ — длина отсека и высота подоконника выглядели незаполненными. Ввод при этом принимает обе формы.
- Считает площади `modelAreas` (`src/model.js`), панель только показывает. **Потолок равен полу** — это одна плоскость. **Стены даём двумя числами**: полная (периметр × высота) — по ней идут обрешётка и утеплитель, которые проходят и за окном; чистая (за вычетом проёмов) — по ней красят и обшивают. Одно число врало бы одному из двух расчётов, а какому — зависит от материала. Проём вычитается из стен ОДНОГО помещения — того же, которому его засчитывает `openingRoom`.
- Рисование считает экранную точку в миллиметры через `viewBox` холста (`data-vb`), дальше решает инструмент: `splitAt` ставит стену ровно там, где её нарисовали (деление пополам врало бы про жест), `nearestSide` + `opPosAt` кладут проём на ближайшую стену по центру тапа.
- Перетаскивание границы считается **в миллиметрах модели** (`viewBox` сам приводит их к экрану), поэтому жест одинаково работает на телефоне и на мониторе. Движение меньше 20 мм границу не двигает — случайный тап не должен менять планировку.
- Вкладки этапов над работами (`specStagesHtml`) показывают те же позиции, что уходят клиенту, но в разрезе стройки: этап → подэтап (группа выбора, помещение или «общее по дому»).
- **Заготовки планировок** (`MODEL_PRESETS` + `presetModel` в `src/model.js`) — типовой контейнер, уже начерченный: отсеки, длины, проёмы. Длины в заготовке **по коробке**, не чистовые: у крайних отсеков отделка съедает ещё и торец, поэтому чистовым 2000 мм на чертеже соответствует 2076. Проём ссылается на изделие **номером в `needs`**, а не по id: заготовка живёт в коде, справочник — в данных. Изделие ищется по виду и РАЗМЕРУ (имена правят и дублируют) — нашлось своё, берём вместе с его ценой; не нашлось, заводим с нулевой, чтобы цену вписал человек, а не выдумала заготовка. Отсек для двери в перегородке заготовка называет НОМЕРОМ (`afterRoom`) — id рождается при сборке модели. Сторожит `test-model-preset.mjs`. Первая заготовка — `c12-san-liv-bed`, контейнер 12,0 × 2,47 м с чертежа заказчика: 4,40 + 14,08 + 7,04 м².

## Спецификация 2 (опытный раздел)

- Раздел правит **ОДИН рабочий лист** (`spec2Sheet` — первый в `specSheets2`), он заводится из заготовки по кнопке «Открыть редактор». Модель обязана лежать в снимке, а не в коде: иначе править её можно было бы только правкой заготовки, и правка терялась бы у всех сразу. До первого нажатия вкладка показывает заготовку и честно об этом говорит.
- Вкладка `spec2` — **схема плана, площади и вход в полноэкранный редактор**. Экрана продажи (списка, формы создания, карточки) в разделе нет намеренно: логику собирают с нуля, и унаследованный экран молча решал бы за неё, как всё должно выглядеть. Сторожит `test-spec2-tab.mjs`.
- **Схема — чертёж, а не план с мебелью**: несущие стены, перегородки, проёмы, марки (Д-1, О-1…), имена помещений и размерные цепочки. Мебели, сантехники и площадей нет — план с диваном отвечает на вопрос «как жить», схема «что строить». Имена комнат и марки при этом обязательны: без них чертёж читают, водя пальцем по цепочкам.
- Геометрия и цепочки — в `modelScheme` (`src/model.js`), в панели только SVG (`modelSchemeSvg`). Сумма любой цепочки равна габариту — это и сторожит `test-model-scheme.mjs`: подпись на чертеже не должна расходиться с моделью. Стена коробки на схеме — это **обшивка** (`finish`): своей толщины у железа контейнера модель не знает, а обрешётка знает, и именно она съедает те сантиметры, из-за которых площади не сходятся с чертежом.
- Рисуем по МОДЕЛИ, а не картинкой: подвинется перегородка — поедет и чертёж, и размеры под ним. Размеры в миллиметрах — так их и замеряют на площадке.
- **Цепочка проёмов меряет РЕЗ в стене, а не изделие** (`cutW` у проёма): по ней размечают лист, а окно уже реза на два монтажных зазора — подписать там габарит изделия значит вырезать проём впритык. Трубы усиления в этот размер НЕ входят: они варятся поверх листа, их внутренняя грань и есть кромка реза (узел 1), поэтому рез = проём между трубами = окно + 30…40. Под маркой стоит вторая строка «рез 1540» в цвете усиления, и она ставится ПРОЧЬ от стены: у нижней стены подпись, уехавшая ещё ниже, ложится на сам чертёж.
- **Лист для бригады печатается целиком** (`buildSchemePrint`, кнопка только на рабочем виде): чертёж, таблица проёмов с колонками «изделие» и «рез в стене», все три узла и пироги слоями, площади помещений. Чертёж и узлы рисует тот же код, что на экране, — распечатка не может показать вчерашний дом. Клиенту печатают другой документ, из спецификации.
- **Усиление проёмов** (`JAMB_TUBE=40`, `JAMB_GAP=20`, `frameNeeded`, `jambs` в `modelScheme`): по обе стороны окна и входной двери стоит труба 40×40 во всю высоту, изделие встаёт МЕЖДУ трубами с зазором 15–20 мм — значит проём режется на 110–120 мм шире изделия, и это то число, по которому работают на площадке. На рабочем виде это два тёмных квадрата в толще стены плюс пояснение рядом с чертежом (`schemeLegend`, числа из тех же констант); клиенту узел монтажа не показываем. В перегородке усиления нет (каркас, варить не во что), у глухого витража тоже — «глухое» изделие опознаётся по раскладке (`face` без открывающихся створок), а не по имени. Изделие без раскладки о себе ничего не сказало, поэтому усиление ему рисуется, а снимается кнопкой у выбранного проёма (`op.frame`) — угадывать за человека, что стоит в этом проёме, нельзя.
- **Перегородка не заезжает на проём** (`openingSpans`, `wallFits`, `moveBoundary(..., winTypes)`): окно режет наружную стену насквозь, и стена, доехавшая до него, — это дыра в стене, а не планировка. Граница останавливается У проёма (вместе с усилением), жест при этом не отменяется; `splitAt` и `splitRoom` в проём стену не ставят вовсе, а панель говорит, что именно мешает. Ширина проёма известна только из `winTypes`, поэтому справочник передаётся в эти функции: без него сторожа нет — молчаливая блокировка «по догадке» была бы необъяснимой.
- **Узлы — вкладками под чертежом** (`NODE_TABS`, `nodeTab`): их три, и листать чертёж сквозь два чужих узла ради нужного значит не смотреть ни на один. Пирог правится ПРЯМО В УЗЛЕ (`pieBlock(sh, key, light)` — один редактор на тёмную боковую панель и светлую карточку), потому что узел и есть то место, где на него смотрят. Кнопки адресуют лист по `data-sh`: на вкладке правится опытный лист, в редакторе — открытый, и перепутать их нельзя.
- **Узлы вынесены и расписаны** (`jambDetailSvg`, `wallDetailSvg`, `schCallout`). На плане труба 40×40 — квадрат в четыре пикселя, а перегородка — две линии: увидеть можно, собрать по ним нельзя. Поэтому на чертеже стоит кружок с подписью («УЗЕЛ 1» — усиление, «УЗЕЛ 2» — перегородка), а сами узлы нарисованы рядом крупно и **без масштаба**: узел показывает, что за чем идёт и какие между этим зазоры, а числа стоят подписями. Подпись выноски ищет свободное место среди уже занятых (тот же `busy`, что у имён помещений) — иначе «УЗЕЛ 1» ложится на марку проёма. **Цифры внутренних цепочек попадают в `busy` ДО выносок**: порядок здесь и есть правило — что посчитано позже, то и наложится.
- **Пироги стен** — перегородки (`WALL_LAYERS` → `model.layers` → `wallThick`) и наружной стены (`SKIN_LAYERS` → `model.skin` → `finish`): списки слоёв с толщинами, правятся на боковой панели редактора (`pieBlock`) и рисуются узлами 2 и 3. Живут в МОДЕЛИ, а не в коде: у каждого дома пирог свой, типовой из кода — умолчание, пока его не тронули; в опытном листе он материализуется при входе в редактор. Пароизоляция 0,1 мм — тоже слой, поэтому толщины считаются в десятых, а в план уходит целое число миллиметров.
- **План идёт ЗА пирогом** (`applyLayers`): толщина стены — это сумма её слоёв, а не отдельное число, которое кто-то вписал руками. Правка слоя тут же двигает `wallThick` / `finish`, и площади пересчитываются следом; отдельного поля «отделка съедает по N мм» у дома со своим пирогом нет — два источника правды про одно число разъезжаются в первый же день. Фактический пирог наружной стены даёт **85 мм** (металл 2 + ППУ 50 + обрешётка 20 + ОСП 9 + фанера 4), а не прежние 76: чистовые размеры от этого меньше, и это правда о доме, а не ошибка расчёта.
- **Два вида одного чертежа** (`SCHEME_VIEWS`, `schemeView`, `schemeParts(sc, view)`): «📐 Размеры» — рабочий, с цепочками, марками и отметками; «🏠 Планировка» — лист клиенту, с именами помещений и площадью пола, без единого размера. Это ОДИН чертёж с параметром, а не два: вторая копия геометрии разошлась бы с первой на первой же правке, и клиент получил бы план, которого не строят. Площадь для клиентского вида приезжает из модели (`labels[].area`), а не считается в панели. **Окна на листе клиента выделены цветом и подписаны размером** (`SCH_WIN`): он читает план окнами — где свет и куда вид; на рабочем чертеже цвет спорил бы с размерными цепочками, а размер там и так стоит под маркой. Дверь размером не подписываем: её читают по створке.
- **Подписи не налезают друг на друга** (`schTextBox` + `schHit`). Марка проёма мельче имени (`SCH_MARK`): это подпись к проёму, а не заголовок комнаты. Двигать её нельзя — она принадлежит своему проёму, поэтому уступает имя: перебирает высоты внутри своей комнаты, потом сдвигается вдоль неё (не выходя за собственные стены — имя в чужой комнате хуже наложения), сначала с запасом, потом хотя бы без пересечения. Занятым считается то, где стоят ЦИФРЫ (марки и числа внутренних цепочек), а не «цепочка целиком»: между полочками остаются просветы, и имени их хватает. Сторожит `test-spec2-tab.mjs` — он разбирает готовый SVG на коробки текста и не терпит ни одного пересечения.
- **На вкладке схема — МИНИАТЮРА, крупно она по тапу** (`spec2SchemeOverlay`, `schemeZoom`). `modelSchemeSvg(model, types, minW)` умеет и то, и другое: `minW=0` вписывает чертёж в колонку целиком, по умолчанию остаётся 560 px. Уезжающий вбок чертёж читается как поломка вёрстки — его листают вслепую и ни разу не видят дом целиком; прокрутка уместна там, где её включает увеличение, то есть в оверлее (ступени 1×/2×/4× — те же, что в редакторе модели: два разных способа увеличить один чертёж пришлось бы объяснять).
- Живым осталось то, что экрана не касается: **свой раздел снимка `specSheets2`** (эксперимент, который пишет в боевые спецификации, — не эксперимент, а авария: по ним заведены договора, объекты и транши), поиск листа по id в обеих коллекциях (`specSheet`), опознание раздела по коллекции (`specIs2` — не по флагу в записи: флаг переживает копирование, и дубль боевого листа считался бы опытным), удаление из обеих (`specDrop`) и развилка расчёта в `src/spec2.js`.
- **`totals2` считает тем же, чем считает боевой раздел**: без правил это прямой `sheetTotals`, с правилами — `allPositions` и те же формулы позиции. Своя копия формул означала бы, что клиенту называют одну цену, а в договор и объект уходит другая, и находится это в лучшем случае на приёмке этапа. Понадобится своя цена — её место в `src/spec2.js`, осознанной развилкой, а не побочным эффектом правки панели.
- **`issues2` спрашивает МОДЕЛЬ, а не отделку**: нет модели → одна строка про модель, дальше претензии самой модели (`modelIssues`). Раздел про коробку, и предупреждение «не выбраны стены» здесь было бы про экран, которого нет.
- **Окна и двери врозь обкатываются здесь, а не в боевых листах** (`modelLab` → `specIs2`). У листа «Спецификации 2» редактор даёт два инструмента вместо одного «Проёма» (`modelTools(lab)`), у каждого свои вкладки «Мои изделия / Каталог» и своё выбранное изделие (`modelPlace={win,door}` — переключение на двери и обратно не должно терять выбранное окно), а карточка ставит вид первой вкладкой (`modelKind`): список, кнопки «добавить» и счётчики идут по одному виду. Вкладка **«Перегородки» есть только у дверей** (`modelKindSides`): окно во внутренней стене — это внутреннее остекление, которого модель не знает, и тап по перегородке инструментом «Окна» ставит окно в ближайшую стену коробки. В боевой «Спецификации» всё это выключено и экран прежний: один «Проём», общий ряд изделий, счётчик «проёмов» — по тем листам заведены договора, объекты и транши, и менять их экран посреди продаж нельзя. Обе половины сторожит `test-model-editor.mjs`.
- **Смета считается ПО ЧЕРТЕЖУ** (`works2` / `modelFacts` / `gaps2` в `src/spec2.js`, вкладка «🧾 Смета» рядом со схемой): количество каждой строки приезжает из модели — площади помещений, число проёмов, раскладка точек, — и у строки печатается, ОТКУДА оно взялось (`positionWhy`: «Окно 4 шт», «стены 41,2 м²»). Число, про которое непонятно, как оно получилось, не проверяют, а принимают на веру или не верят вовсе. Считается на лету и **никуда не сохраняется**: расходиться с чертежом нечему. Расчёт — тот же `sheetPositions`, что собирает объект (`specBuildStages`); своя копия формул означала бы, что на экране одна смета, а в объекте другая, и находится это на приёмке этапа. Лист для расчёта не мутируется — характеристики берутся из модели во временную копию (`probeSheet`).
- **Справки над сметой свёрнуты** (`factsOpen` / `droppedOpen` / `gapsOpen`, `est-facts-open` / `est-dropped-open` / `est-gaps-open`): «откуда числа» показывает в шапке пол, стены и число изделий, «убрано из этого дома» — счёт и сумму со знаком минус, «посчитано, но в смету не попало» — число пробелов. Экран открывают ради сметы, а объёмы и убранное — контекст, к которому обращаются, когда он нужен; развёрнутыми они занимали первый экран целиком, и до первой строки сметы надо было листать. Свёрнутость живёт на экране, в лист не пишется.
- **Материалы строки — ПЕРЕЧНЕМ, а не серой строкой** (`specMatsListHtml`): у каждого своё имя, магазин, цена за единицу, количество и сумма. Три ряда слипшегося текста «Кабель — 1 шт · Гофра — 50 шт · …» не читает никто, а это и есть спецификация. Кнопка «⇄» рядом меняет материал на товар из базы (тот же `datalist`-выбор, что в карточке объекта).
- **Замена материала живёт НА ЛИСТЕ** (`sheet.mats[posKey][oldPid] = newPid`, `applyMatSwaps` в `src/recipe.js`), а не правит смету справочника: справочник общий, и правка в нём поменяла бы состав всех будущих домов. Количество пересчитывается под фасовку нового товара только у площадных позиций — у штучных считались штуки, а не квадраты. По тому же адресу собирается объект и считается подпись состава, поэтому замена доезжает и до стройки, и до «в проекте изменилось» сама. Замена материала В СЛОЕ пирога правит сам пирог (`layer.pid`): у стены один источник правды о том, из чего она сделана.
- **Материал дописывается в строку руками** (`sheet.matAdd[posKey]`, кнопка «+ материал»): смета из справочника описывает типовой дом, а на этом бывает лишний уголок или вторая коробка — дописать его в строке честнее, чем править справочник ради одного дома. Название из базы подтягивает цену, единицу и магазин; без базы цена берётся из формы. Дописанное помечено «добавлен» и убирается крестиком.
- **Материалы в строке переставляются тем же жестом** (`sheet.matOrder[posKey][адрес]`, `matOrderOf` / `sortMats` в `applyMatEdits`; `est-mat-grab` → `est-mat-drop` / `est-mat-step`): взял материал — между соседями раскрылись места «сюда», у взятого стрелки на один шаг. Список читают сверху вниз и по нему закупают: сначала лист, потом крепёж. Порядок живёт НА ЛИСТЕ — в справочнике он общий на все дома. Расставленные руками идут первыми, остальные в порядке сметы, поэтому дописанный материал не уезжает в начало сам. Тот же порядок уходит в объект: показали одно — закупают то же.
- **У СВОЕЙ работы «материал» — это она сама** (`addedPositions`, `own:true`): её имя и цена показаны одним материалом, чтобы деньги считались общим правилом. В списке материалов эта строка НЕ показывается — менять её на товар из базы, переставлять и убирать нечего, а крестик в ней обещал удаление и молча ничего не делал (у такого материала не было ни `pid`, ни `id`, и адрес кнопки уходил пустым). Работа убирается крестиком в СВОЕЙ строке; дописанные к ней материалы живут как обычные, а цена самой работы стоит подписью в шапке списка («работа 500 ₽ · итого 700 ₽»), иначе сумма материалов не сходилась бы с ценой строки. Адрес (`matKeyOf`) теперь есть у КАЖДОГО материала — пустой ключ ломал и количество, и порядок, и замену.
- **Материал можно убрать из строки** (`sheet.matOff[posKey]` — адреса материалов, `matOffOf` / `applyMatEdits`): смета описывает типовой дом, а на этом гофру ведут в кабель-канале. Из СПРАВОЧНИКА при этом не удаляем — он общий, и правка ради одного дома изменила бы состав всех будущих. Убранное остаётся на виду строкой «убрано из этого дома» с возвратом одним тапом: «нет здесь» — это решение, а исчезнувший из списка материал не отличить от потери. Строка, из которой убрали ВСЁ, раскрывается сама — иначе возвращать было бы негде.
- **Количество тоже правится руками** (`sheet.matQty[posKey][pid]`, `applyMatEdits`): чертёж считает честно, но на площадке бывает иначе — подрезка, запас, вторая точка ввода, — и спорить с человеком, который ведёт эту стройку, портал не должен. Ручное число помечено «вручную ⟲», возвращается одним тапом и при замене товара переезжает на новый: человек правил ЭТУ строку, а не карточку каталога.
- **Этап читается БЛОКАМИ ПО ПОМЕЩЕНИЯМ** (`applyRooms` / `roomKeyOf` в `src/recipe.js`, `blocks` в `works2`, `estStageBody` + `blockShut` в панели): «Санузел — стены, пол, потолок», следом «Зал». Правило по помещениям даёт строку на каждую комнату, и этап без блоков читается перечислением поверхностей («стены санузел, стены зал, стены спальня, пол санузел…»), хотя бригада работает комнатой: в санузел заходят один раз и делают там всё. Это ПОРЯДОК, а не новая сущность — группировка стоит последней в конвейере позиций, поэтому один и тот же список уходит и на экран, и в объект; своя группировка в панели означала бы, что дом показан комнатами, а собран россыпью. Порядок блоков — по первому появлению, внутри блока сохраняется ручная перестановка (`posOrder`), а места «сюда» показываются только в блоке взятой строки: работа принадлежит своей комнате по расчёту, и перенос в чужую группировка тут же вернёт. Блок сворачивается (`blockShut` — это про экран, в лист не пишется), заголовок с суммой остаётся всегда. **Сами этапы свёрнуты ПО УМОЛЧАНИЮ** (`stageOpen` — карта про раскрытые, а не про свёрнутые): смета открывается оглавлением из этапов с суммами, и человек разворачивает тот, в который пришёл; сорок строк сразу читаются как простыня.
- **Блок помещения правится руками** (`sheet.posRoom[posKey]`, `posRoomOf` / `ROOM_HOUSE` в `src/recipe.js`; `est-pos-room`, `est-room-name`, «+» в шапке блока). Расчёт знает комнату только там, где по ней считал: обязательные строки справочника посчитаны на весь дом и висят в блоке «Общее по дому», хотя делают их в санузле. Поэтому взятая строка предлагает не только места «сюда», но и КОМНАТЫ — все, включая пустые (блока у них ещё нет), плюс «общее по дому» и «⟲ по расчёту». Приписка меняет только комнату: `why` и цена остаются как посчитано — «на весь дом» и есть правда о том, откуда взялось число. «Общее по дому» хранится своим ключом `"-"`: пустая строка означала бы «человек ничего не решал», и расчёт утащил бы работу обратно. **Имя помещения живёт в МОДЕЛИ** (`modelRoomRename`), а не в листе: то же имя стоит на чертеже и в площадях, вторая копия разошлась бы с ним. «+» в шапке блока кладёт работу сразу в этот этап и в эту комнату (адрес `<лист>@<этап>|<комната>` в `data-k`), а удаление дописанной работы стирает и её отметки (`estForgetKey`) — иначе приписка и этап удалённой строки лежат в снимке вечно.
- **Строка переносится «взял — указал место»** (`estMoveKey` / `estMoveSheet`, `est-pos-grab` → `est-pos-drop`): взятая работа раскрывает между соседями места «сюда» во всю ширину, и одним тапом встаёт куда надо. Стрелки «выше/ниже» просили тап на каждый шаг (восемь тапов, чтобы поднять работу из конца этапа) и умещались в 20 px, в которые на телефоне не попасть. Место указывается МЕЖДУ строками, которые человек видит, то есть вместе с переносимой, — поэтому при вставке индекс сдвигается на единицу (`j>i?j-1:j`). У ВЗЯТОЙ строки есть и шаг на одну позицию (`est-pos-step`, стрелки 26 px): далеко её несут местом «сюда», а на соседнюю строку быстрее тапнуть — и строка остаётся взятой, потому что шагов подряд обычно несколько. Постоянных стрелок в строке нет: три кнопки в каждой строке смету не читают, а тап мимо двадцати пикселей — ровно то, из-за чего прежние стрелки и убрали. Шаг не выходит за своё помещение — сосед из чужой комнаты вернулся бы группировкой тем же рендером. Ключ позиции у листов общий («base:e_osb»), поэтому взятая строка помнит и свой лист: иначе в соседнем проекте подсвечивалась бы его тёзка. Порядок живёт в листе (`posOrder`), справочник общий на все дома. У ЗАГОТОВКИ строку не берут (`canMove` требует живой лист): записывать порядок некуда, и взятая строка повисла бы поднятой навсегда.
- **Строка читается сверху вниз: имя и итог — чипы — управление.** Всё стояло в один ряд, и на узкой колонке имя сжималось до одного слова в строку: поле, чип, итог, ↕, этап и ✕ не сжимаются. Имя занимает всю ширину и не длиннее двух строк (полное — в `title`), итог прижат к правому краю (у всех строк одна колонка), «итого» из раскладки убрано — оно уже стоит справа. Ряд управления — своей строкой, кнопки 28 px. **Выбор этапа показан только у переставленных строк** (`stagePickKey`, кнопка `est-pos-stage-pick`): внутри «ЭТАП 1» у каждой работы стояло «Этап 1» — колонка повторяла заголовок. Чип «за работу» — одним значком ⇄, словом говорим только про исключение («под ключ»). Строки разделяет воздух (`padding:12px 0`), а не полоска: сорок работ, слепленных линиями в пиксель, читаются как простыня.
- **В строке ДВЕ цифры: материалы и работа** (`positionSplit` в `src/recipe.js`, `estSplitHtml` в панели; подытоги этапа — `stage.mats` / `stage.labor` в `works2`). Одна сумма отвечала на вопрос «сколько стоит», но не на те два, которые задают на самом деле: сколько закупать и сколько платить бригаде — это разные решения и разные карманы. Считает разбивку общий модуль, поэтому строка, подытог этапа и объект говорят одно и то же. Своя работа делится по флагу `own` на её материале (её цена — работа, дописанные к ней товары — материалы), а **«под ключ» не делится вовсе**: материалы в эту цифру уже включены, и показать её половинками значит соврать про закупку — там стоит «под ключ N ₽».
- **Цена руками — это цена БРИГАДЕ за работу** (`sheet.posCost[key]` + `sheet.posCostMode[key]`, `applyCost` / `costModeOf` в `src/recipe.js`). «Разводка кабелем — 25 000» это оплата труда, и материалы к ней прибавляются сверху: у работы есть и то, и другое, а одно число вместо двух означало бы, что кабель либо не куплен, либо оплачен дважды. В позиции такая цена лежит в `labor`, в `cost` — материалы плюс она. Пока цену не назначили, **поле ПУСТОЕ с подсказкой «работа»**: подставленный туда итог строки читался как «работа стоит столько же, сколько всё», и вносить оплату было некуда. Рядом с полем стоят **итог строки** крупной цифрой (иначе в шапке нет ни одного числа, пока цена не задана) и **чип «за работу / под ключ» ВСЕГДА**: появляясь только после ввода, он не давал узнать, что у цифры два смысла. Цифра «работа» в раскладке — кнопка: тап ставит курсор в это поле, а тап по «материалам» раскрывает список.
- **Цена СВОЕЙ работы правится в том же поле, но живёт в самой строке** (`posAdd[].cost`, а не `posCost`): отметка поверх расчёта прибавилась бы к её собственной цифре, и работа стоила бы вдвое. Поле показывает её через `positionSplit`, чипа режима у такой строки нет (её цена — всегда работа), а пустой чип «откуда число» не рисуется вовсе: расчёта у неё нет.
- Второй смысл того же числа — **«под ключ»** (`mode:"all"`, `p.costAll`): бригада назвала сумму со своим материалом. Переключается чипом в строке. Умолчание для НОВОГО числа — «за работу» (так его и назначают), а уже введённые до этого числа остаются «под ключ»: менять смысл чужой цифры задним числом нельзя.
- **Варианты — ПЕРЕКЛЮЧАТЕЛЕМ, а не удалением лишних** (`applyPicks`, `sheet.optOf` / `sheet.optPick`). «Утепление — ППУ 3 / 5 / 8 см» это не три работы, а одно решение с тремя ответами. Удаление лишних строк — разовое действие, которое пришлось бы повторять на каждом доме, и в следующем доме уже никто не вспомнит, что вариантов было три; переключатель — одно решение, и по нему видно, что выбор вообще есть. **Портал сам предлагает собрать выбор** (`optSuggest`): заметил рядом «— ППУ 3 см», «— 5 см», «— 8 см» — показал подсказку прямо в списке, с ценами и одной кнопкой. Схлопывать автоматически нельзя («Электрика — кабель» и «Электрика — щиток» это разные работы с общим началом имени), а прятать кнопку в редакторе строки — значит, что её не найдут: предлагаем, решает человек. Кнопка «Собрать в группу» размечает СРАЗУ все строки с тем же началом имени (до « — »): три «Утепления» подряд — одно решение, и объяснять это порталу трижды незачем. Выбор не сделан — в доме первый вариант: молча обнулить дом хуже, чем показать один из них. Метка чипа — часть имени после тире (`optLabelOf`), цена варианта — сумма его строк (правило даёт по строке на помещение). Разметка живёт НА ЛИСТЕ: превратить обязательную смету в вариант в справочнике значит убрать её из состава всех боевых спецификаций, где выбор ещё не сделан.
- **`gaps2` — задание на правила, а не украшение экрана.** Что дом посчитал, а смета не использовала: точки без позиции, поверхности, которыми ничто не меряется, и стоимость самих окон и дверей (в смете только монтаж, изделия живут в `winTypes`). Пока список не пуст, дом продаётся не целиком. У обязательных позиций (`baseEstimates`) площадь всегда нулевая — так считает боевой `sheetPositions`, и трогать это ради опытного раздела нельзя: разъедутся цена на экране и сумма в объекте.

## Правила сборки: чертёж собирает смету

- **Правило говорит одно: К ЧЕМУ применяется смета из справочника** (`src/recipe.js`, раздел снимка `buildRules`, вкладка «⚙️ Правила» в Спецификации 2). «Обшивка стен ОСП — на стены каждого помещения», «Монтаж розетки — на каждую точку». Материалов у правила своих НЕТ: они уже описаны в смете, у неё есть экран, связь с каталогом и история цен, а вторая копия того же разошлась бы с первой на первой правке.
- Считает позицию **та же машинка**, что и спецификацию (`positionFor`, экспортирован из `src/spec.js` ради этого). Своя формула в правилах означала бы, что правило обещает одну сумму, а объект собирается по другой.
- Поля: `what` (`surface` / `point` / `room` / `part` / `house`), `k` (поверхность или вид точки), `scope` (`room` — строка на каждое помещение, `house` — одна на дом), `room` (фильтр по части имени помещения), `qty` (множитель), `stage` (0 = взять из сметы), `off`. Недонастроенное правило **молчит и говорит об этом** (`ruleReady`) — тихий ноль строк не отличить от «правило не сработало».
- **`allPositions` — один список на экран и на объект**: выбранное руками в справочнике плюс то, что дали правила, у каждой строки `from` (`est` / `rule`). `specBuildStages` собирает объект им же — иначе продали одно, а строят другое. `totals2` считает договор оттуда же.
- **Правила даёт только опытный раздел** (`specCtx` в admin.js: `specIs2(sh) ? buildRules : []`). По боевым спецификациям заведены договора, объекты и транши — молча изменить их сумму новым правилом нельзя, сначала правила обкатываются здесь.
- Фильтр помещений — по ЧАСТИ имени, без регистра: типов помещений модель не знает, а «санузел» в имени пишут всегда. Точных ключей у неё нет, и придумывать их значило бы вести второй справочник имён.
- **Правило правится ТАПОМ по чипу «откуда число»** в строке сметы (`est-why` → `estWhyEditor`): чип и есть правило, по которому строка посчитана, и читать его здесь, а править во вкладке «Правила» — значит каждый раз искать нужное среди сорока чужих. Редактор раскрывается у ПЕРВОЙ строки этой сметы (правило по помещениям даёт их несколько, три одинаковых редактора подряд — это не выбор), а само правило заводится ЛЕНИВО, по первой правке (`estRuleSet`): открытый редактор данных не создаёт — человек мог просто посмотреть, откуда взялось число. Новое правило повторяет нынешний счёт («на весь дом»), поэтому первый тап цену не меняет.
- **Правило для сметы ЗАМЕНЯЕТ её обязательную строку** (`ruledEstIds` в `allPositions`): «Контейнер — один раз на дом» и «Контейнер — по площади пола» это одна позиция, посчитанная по-разному, и в списке она обязана быть одна. Позиции ВЫБОРА (отделка комнаты, общедомовая опция) правило не трогает: там решение принято руками. «Убрать правило» возвращает счёт «как в справочнике».
- Правка правила пишется сразу в раздел снимка (`ruleSet`), отдельной кнопки «сохранить» нет — её нет нигде в панели. Имя помещения и множитель пишутся по `change`, а не по `input`: перерисовка на каждой букве выбивает поле из-под пальца.

- Вкладка по умолчанию только у админа (в `rolePermissions` её нет) — открывается ролям в «Права ролей» без правки кода.

## Проекты: дом одной карточкой

- **Раздел снимка `projects`, вкладка «🏗 Проекты»** — дом от чертежа до договора в одном месте. Старая цепочка (смета → шаблон → объект → договор) переписывала состав дома четыре раза, и правка в начале до стройки не доезжала; здесь у дома один адрес, по которому лежит всё.
- **Проект — лист ТОЙ ЖЕ формы, что спецификация** (модель, `specs`, `rooms`/`global`/`qty`, `markup`) плюс `objId` / `contractId` / `clientId`. Поэтому редактор модели, схема, печать бригаде, смета и сборка объекта работают без единой правки: `specSheet` ищет лист и среди проектов, `specDrop` удаляет из всех трёх коллекций, `modelLab` даёт проекту тот же редактор, что опытному листу (окна и двери врозь), `specIssuesOf` спрашивает у проекта МОДЕЛЬ (`issues2`), а не невыбранную отделку.
- **Четыре полосы** (`PROJ_BANDS`, `projBand`): «🧾 Состав» — смета по чертежу, она ПЕРВАЯ и открывается по умолчанию (в проект заходят к смете, её правят каждый день, а чертёж смотрят, когда меняют сам дом); «📐 Чертёж» — схема, площади, печать и вход в редактор; «💰 Деньги» — итоги, наценка, объект и договор; «🏗 Стройка» — этапы созданного объекта. Кнопки «создать объект» и «завести договор» живут ТОЛЬКО на «Деньгах»: две одинаковые кнопки в соседних полосах читаются как два разных действия.
- Объект собирается **тем же `allPositions`**, что показан в «Составе» (`specBuildStages`), договор берёт сумму оттуда же (`specTot` → `totals2`). Это и есть смысл раздела: продали одно — строят то же самое.
- **Чертёж один на два экрана** (`schemeSheet`): схема, узлы, оверлей и печать берут открытый проект, а вне вкладки — опытный лист. Второй набор экранов под проект означал бы вторую копию чертежа, и она разошлась бы с первой.
- Площади в колонке рисует `areasCardHtml` (светлая карточка), а `modelAreasPanel` остаётся тёмной панелью полноэкранного редактора — она свёрстана в 340 px под чёрный фон и в колонку вкладки не встаёт.
- **ПРАВКА ЭКРАНА СМЕТЫ ДЕЛАЕТСЯ СРАЗУ В ОБОИХ РАЗДЕЛАХ.** Смета проекта и смета «Спецификации 2» — это ОДИН экран (`estBodyHtml` + `specMatsListHtml`), и обработчики адресуют лист через `schemeSheet()||spec2Sheet()`. Поэтому новая возможность в строке сметы (замена материала, ручное количество, «+ материал», убрать материал, цена бригаде, перенос строки, варианты) обязана появиться и работать в «Проектах» и в «Спецификации 2» ОДНОВРЕМЕННО — и сторожиться тестами обоих наборов (`test-projects.mjs` и `test-spec2-smeta.mjs`). Заводить возможность в одном разделе и «потом повторить» в другом нельзя: по проектам собирают объекты и договора, и разъехавшиеся экраны означают, что показали одну цену, а построили по другой. Проверять надо оба: живой лист у проекта есть всегда, а у опытного раздела до «Открыть редактор» листа НЕТ — на заготовке то же действие писать некуда.
- **Смета проекта правится там же, где показана**: перечень материалов с заменой и ручным количеством, чип «откуда число», варианты переключателем — всё это общий `estBodyHtml`, поэтому работает и в опытном разделе, и в проекте. Правила сборки раскрываются прямо в полосе «Состав» (`proj-rules`), а не уводят в другой раздел: уходить за ними значит терять из виду дом, ради которого их и правят.
- **Приложили чертёж — портал его читает** (`projStartRead`): после создания проекта с файлом редактор открывается сам и запускается распознавание. Человек выбрал файл; ждать от него ещё одного тапа по кнопке, спрятанной в панели редактора, — это ровно тот случай, когда «портал ничего не сделал» и молча взял заготовку. Прочитанное по-прежнему применяется отдельной кнопкой: пока его не применили, в проекте стоит заготовка.
- Удаление проекта **не трогает объект и договор** — они живут своей жизнью, и об этом сказано в подтверждении: иначе «удалил проект» читается как «удалил всё».
- Вкладка по умолчанию только у админа (в `rolePermissions` её нет). Сторожит `test-projects.mjs`.

## Дом как конструкция: пирог считает себя сам

- **Слой пирога знает не только толщину, но и товар** (`l.pid` → карточка `expProducts`) и свой этап (`l.stage`). Дай слою товар — и стена посчитает себя сама: площадь × цена, тем же `matQtyForArea`, которым считается вся остальная смета (`layerPositions` / `layerMat` / `pieCost` в `src/recipe.js`). Источник здесь — КОНСТРУКЦИЯ, а не справочник: одно место правды о том, из чего сделана стена, вместо двух.
- **Наружная стена меряется ЧИСТОЙ площадью** (`wallNet`): проём режет её насквозь, и в этом месте нет ни одного слоя. Перегородки — своей площадью из модели, причём поперечная считается по ширине контейнера, а продольная (`bay.sub`) по длине своего отсека: считать их одинаково значит выставить счёт за метры, которых нет (`modelTotals.partitionArea`).
- **Слой без товара молчит.** Он описывает конструкцию, но о деньгах ничего не сказал, и придумывать за него цену нельзя; сколько таких слоёв — видно и в узле, и в списке `gaps2`.
- `applyLayers` **бережёт `pid` и `stage`**: правка толщины не сбрасывает товар — слой это не только миллиметры.
- Деньги стоят там же, где пирог (`pieBlock`): «наружная стена · 41,2 м² · 24 720 ₽ (600 ₽/м²)». Узел и есть то место, где на пирог смотрят, и ходить за его стоимостью в смету незачем.
- Пироги включаются тем же ключом, что и правила (`specCtx.pies`): боевые спецификации не видят ни того, ни другого. Конструктивом дом не исчерпывается (печь, сантехника, доставка), поэтому пироги — не замена правилам, а вторая половина: пироги дают стены, правила — остальное.

## Версия проекта вместо копии: «в проекте изменилось»

- Объект собран из проекта и обязан от него отличаться (часы, фото, докупка снабженца), поэтому прямой дифф бессмыслен — нужен третий участник. Им служит **слепок состава** `o.projBase = {at, sig}`, записанный при сборке объекта (`src/projrev.js`). Дальше это то же трёхстороннее сравнение, что у ревизий шаблона, но между ПРОЕКТОМ и стройкой.
- **Версия проекта — это подпись его состава, а не номер.** Состав нигде не хранится: он считается по чертежу и правилам (`allPositions`). Подвинули перегородку — площади поехали, подписи изменились, стройка узнала. Отдельный номер версии двигали бы руками, и он разошёлся бы с содержимым в первый же день.
- **Ключ сопоставления — `w.posKey`** (адрес позиции `p.key`), а не `estId`: одно правило даёт по строке на каждое помещение, и `estId` у них общий. Работу собирает общая машинка `positionWork` (`src/recipe.js`) — ею же считается подпись, иначе «изменилось» загоралось бы на ровном месте.
- Принятие переносит **только план** (имя, цена, материалы). `id` работы, часы, фото и отметку «выполнено» сохраняем; материалы получают свои `id`. Работу со следами стройки (`workTouched`) не убираем, даже если в проекте её больше нет: удалить её значит стереть бригаде день работы.
- Цена переезжает **вместе со своей половиной** (`labor`, `costAll`), а не одним `cost`: пересчёт при следующей загрузке считает цену по материалам и оплате работы, и принятая цифра без `labor` откатилась бы к прежней. То же и в ревизиях шаблона (`objTplApply`).
- **Принятая правка двигает слепок ПО СВОЕЙ позиции** (`projBaseMove`), а не по всему объекту: иначе принятая строка висела бы в списке вечно и уже помеченной спорной — объект-то теперь совпадает с проектом. Спорные при этом остаются на решение человека, а «Ничего не принимать» переписывает слепок целиком.
- Баннер показывается в карточке объекта (`buildProjDiffSection`, рядом с шаблонным) и в полосе «🏗 Стройка» карточки проекта — правку видно там же, где её сделали. Объекты из БОЕВОЙ спецификации баннера не получают: `objProject` отдаёт только проекты.
- Множитель правила умножает **материалы**, а не только сумму: `w.cost` объекта равен сумме материалов, и «×2» в одной цене означало бы, что на стройку уехало вдвое дешевле, чем показано.
- Сторожит `test-proj-revision.mjs`.

## Чтение чертежа: два читателя

- Чертёж читает модель на сервере (`/api/plan-read`), ключ живёт секретом воркера — панель открыта всем, у кого есть пароль админки. Читателей ДВА: **Claude** (`CLAUDE_API_KEY`) и **Kimi/Moonshot** (`KIMI_API_KEY`, OpenAI-совместимый протокол). Ключ может быть не задан или протухнуть — и тогда чтение мертво целиком, хотя всё остальное работает.
- **Меняется конверт, а не правила чтения**: схема ответа (`PLAN_SCHEMA`), системная подсказка (`PLAN_SYSTEM`) и разбор общие; у Kimi свой сборщик запроса (`planRequestOpenAI`) и свой разбор (`planFromOpenAI`). Две копии правил разошлись бы на первой правке, а сверять их пришлось бы человеку по расхождению в метрах.
- Выбор: `PLAN_PROVIDER` (`claude` / `kimi`) — если задан, слушаемся без самодеятельности; иначе читает тот, чей ключ есть, а при двух ключах — Claude, и **только на отказ по ключу (401/403) дочитывает Kimi**. Модель и адрес правятся переменными `KIMI_MODEL` (по умолчанию `kimi-latest`) и `KIMI_BASE_URL` (по умолчанию `https://api.moonshot.ai/v1`).
- **PDF Kimi не принимает**: у OpenAI-совместимого протокола нет блока «документ», и вместо пустого ответа модель об этом не спрашивают — воркер сразу говорит «приложите снимок листа». Claude PDF читает как есть.
- Ошибка чтения несёт с собой, **что вообще настроено** (`providers:{claude,kimi}` → в алерте «Настроено на воркере: Claude ✓ · Kimi —»): «чертёж не читается» и «ключ не тот» чинятся по-разному, а по тексту модели их не различить. Значения ключей в ответ не попадают никогда — только факт, что ключ задан.
- В ответе и на экране сверки написано, **кто прочитал** (`provider` + модель): человек сверяет метры и должен знать, чьи они. Сторожат `test-plan-read.mjs` (конверт) и `test-plan-provider.mjs` (выбор читателя на настоящем `worker.fetch`).

## Вход и защита от перебора

- PIN — четыре цифры, а `/api/login` и `/api/client-login` открыты без авторизации, поэтому в Worker есть сторож `login_guard` (таблица создаётся сама): 5 неудач по личности или 25 по адресу за 15 минут закрывают вход на 15 минут, каждая неудача ещё и тормозится на 400 мс.
- Счёт по ДВУМ ключам: личность (нормализованный телефон / договор) и IP. Порог по адресу выше — бригада на объекте сидит за общим мобильным NAT, и опечатки коллег не должны запирать вход всем.
- Сбой D1 в стороже — **fail-open**: вход продолжает работать. Запереть всю компанию снаружи портала хуже, чем пропустить перебор в момент, когда база и так лежит.
- Ответ на неудачу ОДИН и тот же на «нет такого телефона» и «PIN не тот» (`Неверный телефон или PIN`, у клиента — `Договор не найден или неверный PIN`). Раздельные тексты позволяли перебором узнать, кто работает в компании и кто у неё в клиентах. `PIN не задан` — исключение: это незаконченная настройка, а не перебор, и в счётчик не пишется.
- Успешный вход обнуляет счётчики. PIN пока хранится в снимке открытым (`users[].pin`) — от неадминов вырезается при чтении; переход на хеш потребует решить, как админ сообщает сотруднику забытый PIN.

## Тесты

`npm test` (`tools/run-tests.mjs`) прогоняет ВСЕ наборы `tools/test-*.mjs` — каждый отдельным процессом, потому что панельные наборы держат общий стейт в `node:vm`. Новый файл `tools/test-*.mjs` подхватывается сам, правок в package.json и CI не нужно.

- Общие модули: `test-stage-schedule` — сроки этапов (`src/stages.js`), `test-model` — модель контейнера (`src/model.js`), `test-recipe` — правила сборки (`src/recipe.js`), `test-proj-revision` — версии проекта (`src/projrev.js`).
- Сквозные: `test-spec` — расчёт спецификации (`src/spec.js`), `test-spec-sheet` — вкладка «Спецификация» целиком: копия планировки, выбор вариантов, печать клиенту, договор и объект из спеки. `test-photo-queue` — офлайн-очередь фото, `test-selection` — выбор клиента и бюджет, `test-tpl-revision` — «в шаблоне изменилось», `test-stock` — склад остатков (перекуп → склад → выдача, без двойного расхода), `test-acceptance` — приёмка этапа и транши, обе половины (панель + ручка Worker'а).
- Панель (`tools/harness/panel-vm.js` — admin.js в `node:vm` с поддельным DOM, стейт синтетический): `test-supply-group` — групповая правка закупки, `test-material-link` — связь с каталогом, `test-mat-change` — заявка на замену, `test-state-sync` — что именно уходит в облако и что держат стражи (`boot({net})` подменяет fetch).
- Worker/бот (моки D1 и fetch, гоняют настоящий `worker.fetch`): `test-login-guard` — вход и перебор PIN, `test-state-api` — версия снимка и скоуп оптимистичной блокировки, `test-botissue`, `test-issue-escalation`, `test-stt`, `test-ogg`.

**CI гоняет их перед выкатом:** в `deploy.yml` есть job `test`, оба деплой-job'а стоят на `needs: test` — упавший тест останавливает выкат целиком. Всё равно гоняйте локально перед пушем в `main`: прогон ~3 с.

## История действий (вкладка «🕘 История»)

- Лог пишет **Worker**, а не панель: `postState` читает снимок «до», `src/audit.js` сравнивает его с пришедшим и записывает разницу в отдельную таблицу D1 `audit_log`. В `admin.js` логирования нет и добавлять не надо — новые действия попадают в историю сами.
- Автор берётся из подписанного токена (`auth.uid`), время — серверное; из панели запись не подделать. Таблица append-only, эндпоинта на правку/удаление нет.
- В снимок лог НЕ кладём (лимит 2 МБ на строку). Разделы без метки в `SECTION_LABELS` не логируются; секретные поля (`pin`, `token`, …) пишутся как `•••`.
- Дёшево за счёт сравнения СЫРЫХ строк JSON по разделам: неизменившееся отсеивается без парсинга. Пишется в `ctx.waitUntil` — сохранение панели не тормозит.
- Правки одного поля в течение 2 минут склеиваются в одну запись (`cnt`), иначе посимвольный ввод давал бы десяток строк.
- `GET /api/audit`: админ видит весь портал, обычный сотрудник — только свои действия (сервер подменяет `uid`), клиент — 403.

## Полевой режим: очередь фото

- Стейт офлайн переживает всё (localStorage-кэш + дожим при уходе), а фото до этого терялось: один `fetch` без сети — и отчёт о работе пропадал с алертом. Файл кладётся в **IndexedDB** (`kubr_uploads`) и досылается сам.
- Прикрепление к работе делает ТА ЖЕ очередь (`photoAttach`), а не загрузка: иначе фото уехало бы в R2, а в объекте его бы не было. Битую ссылку в стейт не пишем — её потом не отличить от настоящей.
- Досылка останавливается на первой сетевой ошибке: связи всё ещё нет, перебирать остальные — жечь батарею. Запускается на `online`, на возврате во вкладку, на старте циклов и раз в минуту, пока очередь не пуста.
- Автор и время берутся из момента СЪЁМКИ, а не отправки. Если работу за это время удалили, элемент из очереди убирается — иначе она копится вечно.
- Хранилище подменяемо (`_uploadStore`), поэтому логика очереди тестируется без браузера (`test-photo-queue`).

## Гочи процесса

- **`gid()` обязан быть уникальным гарантированно** (`Date.now()` + счётчик вкладки + случайность). На id висят отметки закупки, фото и часы: два материала с одним id — это «куплено», поставленное не тому. Времени и трёх случайных символов не хватало — сборка объекта заводит сотню id в одну миллисекунду, а 36³ вариантов дают там коллизию примерно в каждом шестом прогоне; ловил это `test-spec-sheet` («id уникальны»), причём падал он редко и в CI, а не локально.

- В репо иногда работают параллельные Claude-сессии: перед коммитом проверять `git diff --stat`, коммитить только свои файлы (не `git commit -am`).
- Стейл-вкладка со старым кодом однажды затёрла облачный стейт (восстанавливали через D1 Time Travel). Против этого работают страж сохранения и «дожим при уходе» в admin.js — при правках зоны сохранения не ослаблять эти механизмы.
