# Портал КубрДом

Портал строительной компании (бани и дома из контейнеров): CRM, объекты, сметы, договоры, снабжение, табель рабочих. Язык проекта и общения — русский.

Прод: **https://portal.kubrdom.ru** (свой домен обязателен: `*.pages.dev` / `*.workers.dev` в РФ режутся по SNI). Админ-панель: `/admin`.

## Архитектура

- **Cloudflare Pages** `kubrdom-portal` — фронт React/Vite (src/ → dist/) + **standalone админ-панель** `public/admin.html` + `public/admin.js` (~700 КБ vanilla JS — основной код панели).
- **Worker** `kubrdom-portal-api` (`src/worker.js`) + **D1** `banya-db` + **R2** `kubrdom-files` (фото/документы) + Telegram-зеркало фото/видео (бот, супергруппа с темами по объектам).
- `functions/api/[[path]].js` (Pages Function) проксирует `/api/*` → Worker на стороне edge — это обход блокировки workers.dev в РФ, НЕ ломать. Клиент ходит same-origin (`API_BASE=""`), файловые URL относительные (`/api/file/<key>`).
- Панель синхронизируется снимком всего стейта в D1 (`storage_key=admin_panel`), автосейв + live-опрос; авторизация заголовком `X-Admin-Token` (секрет `ADMIN_TOKEN` на Worker, fail-closed).
- **Опрос чужих правок спрашивает только версию** — `GET /api/state/:key/version` отдаёт `max(updated_at)`, и полный снимок (~1 МБ) тянется лишь когда версия выросла. Не возвращать опрос к «каждые 15 с тянем всё»: это мегабайт четыре раза в минуту на телефон бригадира. Если версия не пришла (старый Worker в окне деплоя отдаёт 404) — клиент сам падает на полный опрос.

## Деплой

- **Автодеплой: пуш в `main` → GitHub Actions** (Pages + Worker, секрет `CLOUDFLARE_API_TOKEN` комплексный). Ручной wrangler не нужен.
- **Commit-сообщения — ASCII-чистые**: кириллица/грязные байты роняют Pages-деплой (`Invalid commit message [8000111]`).
- Новый секрет в deploy.yml: СНАЧАЛА `gh secret set <NAME>` (хоть плейсхолдером), ПОТОМ пушить код со ссылкой — иначе job падает.
- После `git push` не брать `gh run list --limit 1` сразу (поймаешь предыдущий прогон) — матчить run по `headSha`.
- Секрет `TG_BOT_TOKEN` задан вручную на Worker и переживает деплои — CI его не трогает.

## Сборка админ-панели (не ломать!)

- `npm run build` = `vite build` + `build:admin` (esbuild `public/admin.js` → `dist/admin.js`, target **es2017**).
- `admin.js` — ВНЕШНИЙ файл. НЕ инлайнить обратно в admin.html: >700 КБ инлайн-скрипта мобильный Safari не тянет (белый экран).
- target es2017: `?.`/spread транспилируются, но `async/await` остаётся НАТИВНЫМ. Не опускать target ниже — regenerator-полифил вешал iOS.
- Проверка после деплоя: в задеплоенном admin.js `?.` = **0 вхождений**. Размер — ориентир, а не константа: он растёт с кодом (на 2026-08-28 ~1650 КБ). Сверять надо порядок величины, а не точное число.
- Кириллицу esbuild экранирует в `\uXXXX` с ЗАГЛАВНЫМИ hex, поэтому `grep "Можно делать"` по задеплоенному бандлу **ничего не найдёт**. Проверять деплой по ASCII-маркерам (`data-a`-именам, id, классам).
- `<meta viewport>` содержит `maximum-scale=1` (лечит авто-зум iOS на инпутах) — не убирать.

## Критичные правила данных

- **Лимит D1: строка ≤ 2 МБ.** Снимок сохраняется одним транзакционным batch — одна раздутая строка откатывает ВСЁ сохранение. Поэтому файлы (фото, PDF, договоры) ВСЕГДА в R2 ссылками, НИКОГДА не base64 в стейт.
- Загрузка файлов: клиент жмёт фото до ≤1 МБ, Worker принимает img+pdf+office до 20 МБ по allowlist расширений (SVG/HTML запрещены — XSS).
- Частые микро-обновления UI — через `rerenderTab()` (частичная перерисовка `#tab-content`), не полный `render()` (дёргает скролл на iOS).
- Паспортные данные шаблона договора живут ТОЛЬКО в localStorage (`kubr_ctTpl`), в снимок D1 не попадают — так и оставить.

## Материалы: каталог → смета → шаблон → объект → закупка

- **`m.pid` — ссылка позиции на карточку каталога** (`expProducts`). Имя/цена/магазин остаются КОПИЕЙ: объект живёт своей сметой и не переписывается при правке базы. Раньше связь рвалась в `_tplEstWork` (материал становился снимком по имени), и «где используется» собрать было не из чего. Совпадение по имени связью не считать: имена правят и дублируют.
- Исторические позиции привязывает `ensureMatPids()` при загрузке — только при ТОЧНОМ совпадении имени и когда в каталоге такой товар один. Тёзки остаются без `pid`: привязка к чужой карточке потом меняла бы не тот товар.
- Карточка товара показывает «Где используется» (шаблоны, объекты, работы) и расхождение цены. **Синхронизация цены — только вручную и с выбором области** (`matApplyCatalogPrice`): цена в объекте — согласованный бюджет, а не витрина.
- **`w.cost` в портале ВСЕГДА равен сумме материалов** (`wMatTotal`). Меняете цену или количество материала — пересчитывайте `w.cost` тут же; `normalizeWorkCosts()` чинит это лишь при следующей загрузке.
- Замена товара снимает отметки закупки (`supplyClearMarks`) и **отвязывает** позицию партии (`needId=null`), а не удаляет её: деньги реально потрачены и должны остаться в сумме партии. Правка цены заменой НЕ считается — отметки сохраняются.
- Объединённая строка закупки (`_mergeMats`) правится целиком: имя/цена/магазин на все потребности, количество у каждой своё. Строка слепляет позиции по УСЕЧЁННОМУ имени (`normMatName`: «ОСП 30 м²» и «ОСП 18 м²» → одна «ОСП»), поэтому в модалке показываются собственные имена — иначе замена молча переименует обе фасовки.

## Заявка на замену материала

- Замена по ходу стройки — это деньги: снабженец видит разницу со сметой ДО сохранения, а разница от `settings.matChangeLimit` (по умолчанию 10 000 ₽) уходит заявкой тому, кто отвечает за деньги. Порог правится прямо в модалке теми, кто согласовывает.
- Заявка — обычный вопрос по объекту с `kind:"matchg"` (`matChangeRequest`), поэтому у неё сразу есть адресат, возраст, эскалация и Telegram. Сама правка лежит в `t.mat`, применяется кнопкой «✅ Применить замену» ТЕМ ЖЕ кодом, что и прямое сохранение (`matChangeApply`) — иначе «согласовано» и «сделано» разъедутся.
- `payer:"client"` при подорожании заводит строку в `extraWorksPlan` договора: иначе замена молча становится убытком компании. `payer:"company"` — не заводит.
- Пока заявка открыта, позиция в снабжении помечена «⏳ замена на согласовании» (`matPendingChange`): без этого уходит вторая такая же заявка, а бригадир не понимает, почему материал прежний.
- Вид `matchg` помечен `auto:true` и в форме «новый вопрос» не показывается: без payload'а такая заявка бессмысленна.

## Вход и защита от перебора

- PIN — четыре цифры, а `/api/login` и `/api/client-login` открыты без авторизации, поэтому в Worker есть сторож `login_guard` (таблица создаётся сама): 5 неудач по личности или 25 по адресу за 15 минут закрывают вход на 15 минут, каждая неудача ещё и тормозится на 400 мс.
- Счёт по ДВУМ ключам: личность (нормализованный телефон / договор) и IP. Порог по адресу выше — бригада на объекте сидит за общим мобильным NAT, и опечатки коллег не должны запирать вход всем.
- Сбой D1 в стороже — **fail-open**: вход продолжает работать. Запереть всю компанию снаружи портала хуже, чем пропустить перебор в момент, когда база и так лежит.
- Ответ на неудачу ОДИН и тот же на «нет такого телефона» и «PIN не тот» (`Неверный телефон или PIN`, у клиента — `Договор не найден или неверный PIN`). Раздельные тексты позволяли перебором узнать, кто работает в компании и кто у неё в клиентах. `PIN не задан` — исключение: это незаконченная настройка, а не перебор, и в счётчик не пишется.
- Успешный вход обнуляет счётчики. PIN пока хранится в снимке открытым (`users[].pin`) — от неадминов вырезается при чтении; переход на хеш потребует решить, как админ сообщает сотруднику забытый PIN.

## Тесты

`npm test` (`tools/run-tests.mjs`) прогоняет ВСЕ наборы `tools/test-*.mjs` — каждый отдельным процессом, потому что панельные наборы держат общий стейт в `node:vm`. Новый файл `tools/test-*.mjs` подхватывается сам, правок в package.json и CI не нужно.

- Панель (`tools/harness/panel-vm.js` — admin.js в `node:vm` с поддельным DOM, стейт синтетический): `test-supply-group` — групповая правка закупки, `test-material-link` — связь с каталогом, `test-mat-change` — заявка на замену.
- Worker/бот (моки D1 и fetch, гоняют настоящий `worker.fetch`): `test-login-guard` — вход и перебор PIN, `test-state-api` — версия снимка и скоуп оптимистичной блокировки, `test-botissue`, `test-issue-escalation`, `test-stt`, `test-ogg`.

**CI гоняет их перед выкатом:** в `deploy.yml` есть job `test`, оба деплой-job'а стоят на `needs: test` — упавший тест останавливает выкат целиком. Всё равно гоняйте локально перед пушем в `main`: прогон ~3 с.

## История действий (вкладка «🕘 История»)

- Лог пишет **Worker**, а не панель: `postState` читает снимок «до», `src/audit.js` сравнивает его с пришедшим и записывает разницу в отдельную таблицу D1 `audit_log`. В `admin.js` логирования нет и добавлять не надо — новые действия попадают в историю сами.
- Автор берётся из подписанного токена (`auth.uid`), время — серверное; из панели запись не подделать. Таблица append-only, эндпоинта на правку/удаление нет.
- В снимок лог НЕ кладём (лимит 2 МБ на строку). Разделы без метки в `SECTION_LABELS` не логируются; секретные поля (`pin`, `token`, …) пишутся как `•••`.
- Дёшево за счёт сравнения СЫРЫХ строк JSON по разделам: неизменившееся отсеивается без парсинга. Пишется в `ctx.waitUntil` — сохранение панели не тормозит.
- Правки одного поля в течение 2 минут склеиваются в одну запись (`cnt`), иначе посимвольный ввод давал бы десяток строк.
- `GET /api/audit`: админ видит весь портал, обычный сотрудник — только свои действия (сервер подменяет `uid`), клиент — 403.

## Гочи процесса

- В репо иногда работают параллельные Claude-сессии: перед коммитом проверять `git diff --stat`, коммитить только свои файлы (не `git commit -am`).
- Стейл-вкладка со старым кодом однажды затёрла облачный стейт (восстанавливали через D1 Time Travel). Против этого работают страж сохранения и «дожим при уходе» в admin.js — при правках зоны сохранения не ослаблять эти механизмы.
