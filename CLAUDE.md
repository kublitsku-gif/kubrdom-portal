# Портал КубрДом

Портал строительной компании (бани и дома из контейнеров): CRM, объекты, сметы, договоры, снабжение, табель рабочих. Язык проекта и общения — русский.

Прод: **https://portal.kubrdom.ru** (свой домен обязателен: `*.pages.dev` / `*.workers.dev` в РФ режутся по SNI). Админ-панель: `/admin`.

## Архитектура

- **Cloudflare Pages** `kubrdom-portal` — фронт React/Vite (src/ → dist/) + **standalone админ-панель** `public/admin.html` + `public/admin.js` (~700 КБ vanilla JS — основной код панели).
- **Worker** `kubrdom-portal-api` (`src/worker.js`) + **D1** `banya-db` + **R2** `kubrdom-files` (фото/документы) + Telegram-зеркало фото/видео (бот, супергруппа с темами по объектам).
- `functions/api/[[path]].js` (Pages Function) проксирует `/api/*` → Worker на стороне edge — это обход блокировки workers.dev в РФ, НЕ ломать. Клиент ходит same-origin (`API_BASE=""`), файловые URL относительные (`/api/file/<key>`).
- Панель синхронизируется снимком всего стейта в D1 (`storage_key=admin_panel`), автосейв + live-опрос; авторизация заголовком `X-Admin-Token` (секрет `ADMIN_TOKEN` на Worker, fail-closed).
- **Сейв шлёт ТОЛЬКО изменившиеся разделы** (`dirtySections`). Не возвращать «шлём весь снимок»: сторож `base` на сервере проверяет ровно те `work_id`, что пишутся, поэтому запись всех разделов подряд означала 409 всем остальным на любую чужую правку. Форс-сохранение («Сохранить как есть») — исключение, оно шлёт всё и без `base`.
- Эталон стража (`updateServerCounts(items, onlyKeys)`) после такого сейва двигается только по отправленным разделам: по остальным сервер ничего не подтверждал, и записать туда локальный счёт значит обезоружить стража там, где вкладка устарела.
- **Опрос чужих правок спрашивает только версию** — `GET /api/state/:key/version` отдаёт `max(updated_at)`, и полный снимок (~1 МБ) тянется лишь когда версия выросла. Не возвращать опрос к «каждые 15 с тянем всё»: это мегабайт четыре раза в минуту на телефон бригадира. Если версия не пришла (старый Worker в окне деплоя отдаёт 404) — клиент сам падает на полный опрос.

## Деплой

- **Автодеплой: пуш в `main` → GitHub Actions** (Pages + Worker, секрет `CLOUDFLARE_API_TOKEN` комплексный). Ручной wrangler не нужен.
- **Commit-сообщения — ASCII-чистые**: кириллица/грязные байты роняют Pages-деплой (`Invalid commit message [8000111]`).
- Новый секрет в deploy.yml: СНАЧАЛА `gh secret set <NAME>` (хоть плейсхолдером), ПОТОМ пушить код со ссылкой — иначе job падает.
- После `git push` не брать `gh run list --limit 1` сразу (поймаешь предыдущий прогон) — матчить run по `headSha`.
- Секрет `TG_BOT_TOKEN` задан вручную на Worker и переживает деплои — CI его не трогает.

## Сборка админ-панели (не ломать!)

- `npm run build` = `vite build` + `build:admin` (esbuild `public/admin.js` → `dist/admin.js`, target **es2017**).
- `admin.js` — ВНЕШНИЙ файл. НЕ инлайнить обратно в admin.html: >700 КБ инлайн-скрипта мобильный Safari не тянет (белый экран).
- target es2017: `?.`/spread транспилируются, но `async/await` остаётся НАТИВНЫМ. Не опускать target ниже — regenerator-полифил вешал iOS.
- Проверка после деплоя: в задеплоенном admin.js `?.` = **0 вхождений**. Размер — ориентир, а не константа: он растёт с кодом (на 2026-08-28 ~1650 КБ). Сверять надо порядок величины, а не точное число.
- Кириллицу esbuild экранирует в `\uXXXX` с ЗАГЛАВНЫМИ hex, поэтому `grep "Можно делать"` по задеплоенному бандлу **ничего не найдёт**. Проверять деплой по ASCII-маркерам (`data-a`-именам, id, классам).
- `<meta viewport>` содержит `maximum-scale=1` (лечит авто-зум iOS на инпутах) — не убирать.

## Критичные правила данных

- **Лимит D1: строка ≤ 2 МБ.** Снимок сохраняется одним транзакционным batch — одна раздутая строка откатывает ВСЁ сохранение. Поэтому файлы (фото, PDF, договоры) ВСЕГДА в R2 ссылками, НИКОГДА не base64 в стейт.
- Загрузка файлов: клиент жмёт фото до ≤1 МБ, Worker принимает img+pdf+office до 20 МБ по allowlist расширений (SVG/HTML запрещены — XSS).
- Частые микро-обновления UI — через `rerenderTab()` (частичная перерисовка `#tab-content`), не полный `render()` (дёргает скролл на iOS).
- Паспортные данные шаблона договора живут ТОЛЬКО в localStorage (`kubr_ctTpl`), в снимок D1 не попадают — так и оставить.

## Сроки по этапам

- План живёт НА ЭТАПЕ объекта: `s.planStart` / `s.planEnd` (обе необязательные). Дедлайн договора говорит про сдачу целиком и загорается, когда всё уже сорвано; этап — то, чем стройка меряется на площадке.
- **Факт не храним** — выводим из следов работы (`timeLogs`, `doneAt`) в `stageFact`. Отдельное поле пришлось бы вести руками, и оно разошлось бы с работами при первой правке. Конец этапа показываем, только когда закрыты ВСЕ работы: иначе «закончен такого-то» читается как сдача.
- Логика — в `src/stages.js`, общая с напоминаниями (как `src/supply.js` для закупок). В `admin.js` только показ: плашка в шапке этапа, строка худшего этапа на карточке в списке. Не дублировать расчёт в панели — чат и экран разойдутся.
- Состояния: `overdue` (план кончился, этап открыт), `notStarted` (пора было начать, следов нет), `soon` (≤2 рабочих дней), `go`, `lateDone`, `done`, `none`. Счёт в РАБОЧИХ днях, как у дедлайнов.
- В Telegram уходят только `overdue` / `notStarted` / `soon` (`stagesNeedingAttention`, утренний крон): рассылка про идущие в сроке этапы — спам, из-за которого бота мьютят.
- План правится в карточке объекта в режиме правки (`obj-stage-plan`), запись по `change`, а не по `input`: нативный date-инпут шлёт input на каждую цифру года, и перерисовка выбивала бы календарь из-под пальца.

## Ревизии шаблона: «в шаблоне изменилось»

- Объект — глубокая копия шаблона (`reidStages`), и отличаться он ОБЯЗАН: он живёт своей сметой. Поэтому дифф «объект против шаблона» бессмыслен, нужен третий участник — слепок шаблона на момент создания объекта (`o.tplBase`, пишется в `add-obj`). Дальше это обычное трёхстороннее сравнение, как при слиянии снимков.
- Храним не содержимое, а короткие подписи работ (`workSig`, FNV-хэш от имени, цены и материалов): полный слепок сорока работ весил бы десятки килобайт в КАЖДОМ объекте, а раздел `objects` и так ближе всех к лимиту строки D1.
- Ключ сопоставления между копиями — `estId`: `reidStages` выдаёт новые id, а `estId` копирование переживает. Работы без `estId` (докупка снабженца, ручные) не сравниваются вовсе.
- `safe:true` — объект свою копию не трогал, принять можно молча. Правка с двух сторон помечается спорной, и решает человек.
- Принятие переносит ТОЛЬКО план (имя, цену, материалы). `id` работы, часы, фото и отметку «выполнено» сохраняем — иначе принятая правка обнуляет бригаде день работы. Материалы получают свои `id`: общий id «протёк» бы отметками закупки между объектами.
- «Ничего не принимать» просто сдвигает слепок. Без этого отклонённая правка всплывает в каждом рендере, и баннер становится фоном, который не читают.

## Приёмка этапа и график платежей

- Транш живёт в договоре: `c.tranches = [{id, title, amount, stageId, paidAt, paidBy}]`. Привязка к ЭТАПУ — суть механизма: клиент принимает этап, и сумма становится «к оплате». Это единственное место, где «сделано» встречается с «оплачено».
- Приёмка живёт на этапе объекта: `s.acceptance = {askedAt, askedBy, acceptedAt}`. Запрос приёмки — отдельное действие производства, а не автоматика по «все работы закрыты»: закрытая галочка иногда стоит раньше фактической готовности.
- **Отметку о приёмке ставит СЕРВЕР** (`POST /api/client/accept-stage`), потому что `postState` для клиента read-only — его частичный срез затёр бы базу. Ручка проверяет по токену, что этап принадлежит объекту ЕГО договора, и пишет через `writeSection` с проверкой `updated_at` (между чтением и записью панель могла сохранить объекты).
- После приёмки Worker заводит обычный вопрос `kind:"money"` финансисту с суммой транша — так у «выставить счёт» сразу есть адресат, возраст, эскалация и Telegram. Повторную приёмку и повторный вопрос сторожит фиксированный id `iss_acc_<stageId>`.
- Оплату транша отмечает руками тот, кто ведёт кассу. Автоматически по приходам не угадываем: один платёж закрывает то один транш, то половину другого, а ошибка здесь — неверный счёт клиенту.
- В «Финансах» принятые, но не оплаченные этапы висят блоком «К оплате»: этих денег не видно ни в приходах (ещё не пришли), ни в P&L (он про план).

## Материалы: каталог → смета → шаблон → объект → закупка

- **`m.pid` — ссылка позиции на карточку каталога** (`expProducts`). Имя/цена/магазин остаются КОПИЕЙ: объект живёт своей сметой и не переписывается при правке базы. Раньше связь рвалась в `_tplEstWork` (материал становился снимком по имени), и «где используется» собрать было не из чего. Совпадение по имени связью не считать: имена правят и дублируют.
- Исторические позиции привязывает `ensureMatPids()` при загрузке — только при ТОЧНОМ совпадении имени и когда в каталоге такой товар один. Тёзки остаются без `pid`: привязка к чужой карточке потом меняла бы не тот товар.
- Карточка товара показывает «Где используется» (шаблоны, объекты, работы) и расхождение цены. **Синхронизация цены — только вручную и с выбором области** (`matApplyCatalogPrice`): цена в объекте — согласованный бюджет, а не витрина.
- **`w.cost` в портале ВСЕГДА равен сумме материалов** (`wMatTotal`). Меняете цену или количество материала — пересчитывайте `w.cost` тут же; `normalizeWorkCosts()` чинит это лишь при следующей загрузке.
- Замена товара снимает отметки закупки (`supplyClearMarks`) и **отвязывает** позицию партии (`needId=null`), а не удаляет её: деньги реально потрачены и должны остаться в сумме партии. Правка цены заменой НЕ считается — отметки сохраняются.
- Объединённая строка закупки (`_mergeMats`) правится целиком: имя/цена/магазин на все потребности, количество у каждой своё. Строка слепляет позиции по УСЕЧЁННОМУ имени (`normMatName`: «ОСП 30 м²» и «ОСП 18 м²» → одна «ОСП»), поэтому в модалке показываются собственные имена — иначе замена молча переименует обе фасовки.

## Склад остатков

- Раздел снимка `stock` — то, что физически осталось и ждёт следующей стройки: `[{id, pid, n, mode, cost, store, qty, srcObjId, srcObjName, at, by}]`. Одинаковые позиции складываются в одну строку, нулевая строка удаляется.
- Кандидат в остаток — **перекуп** (`needOverBought`: куплено больше, чем требует смета). Это единственная величина, которую портал знает точно: фактический расход на объекте никто не считает.
- Сопоставление остатка с потребностью — по `pid`, имя только запасной путь для позиций без ссылки. «ОСП 30 м²» и «ОСП 18 м²» — разные фасовки, молча считать их одним товаром нельзя.
- `stockCoverNeeds` берёт по каждой потребности ровно нехватку, а не «сколько есть»: иначе на объект уезжает лишнее и там снова копится остаток.
- Выдача создаёт партию с `fromStock:true`. Такая партия **в кассу не проводится** — деньги за этот материал ушли раньше, на прошлом объекте, и второй расход был бы двойным счётом. Она же исключена из счётчика «не проведено», иначе финансист видит долг, который нечем закрыть. Приёмку не подделываем: материал ещё надо довезти, мастер отмечает её как обычно.

## Заявка на замену материала

- Замена по ходу стройки — это деньги: снабженец видит разницу со сметой ДО сохранения, а разница от `settings.matChangeLimit` (по умолчанию 10 000 ₽) уходит заявкой тому, кто отвечает за деньги. Порог правится прямо в модалке теми, кто согласовывает.
- Заявка — обычный вопрос по объекту с `kind:"matchg"` (`matChangeRequest`), поэтому у неё сразу есть адресат, возраст, эскалация и Telegram. Сама правка лежит в `t.mat`, применяется кнопкой «✅ Применить замену» ТЕМ ЖЕ кодом, что и прямое сохранение (`matChangeApply`) — иначе «согласовано» и «сделано» разъедутся.
- `payer:"client"` при подорожании заводит строку в `extraWorksPlan` договора: иначе замена молча становится убытком компании. `payer:"company"` — не заводит.
- Пока заявка открыта, позиция в снабжении помечена «⏳ замена на согласовании» (`matPendingChange`): без этого уходит вторая такая же заявка, а бригадир не понимает, почему материал прежний.
- Вид `matchg` помечен `auto:true` и в форме «новый вопрос» не показывается: без payload'а такая заявка бессмысленна.

## Позиции «выбор клиента»

- `m.sel` — позицию выбирает клиент (плитка, печь, двери, сантехника), и сумма в смете становится **бюджетом выбора** (`matSelBudget`). `m.selDue` — до какого числа, `m.selDone` — когда выбор состоялся.
- Правило вместо порога: дешевле или вровень с бюджетом — замена идёт без бумаг; **дороже — согласование всегда**, каким бы ни был `matChangeLimit`. Это уже не наша экономия, а счёт клиенту, и решать за него снабженец не может.
- В форме замены у такой позиции по умолчанию стоит «за счёт клиента» — видимый выбор, а не подмена при отправке. Применённая замена ставит `selDone`, но `sel` НЕ снимает: по метке видно, чья это была позиция и сколько закладывали.
- Предикат общий (`pendingSelections` в `src/supply.js`): по нему рисует плашки панель, показывает список кабинет клиента и шлёт утреннее напоминание крон — «просрочен» на экране и в чате обязан совпадать. Напоминание уходит сопровождению и руководству, не бригаде: разговаривать с клиентом — их работа.
- Клиенту показываем бюджет словом «заложено», а не «доплатите»: иначе выбор превращается в спор постфактум.

## Спецификация дома: продажа собирает объект

- Продавец собирает дом клиенту из планировки: помещение → отделка помещения. Раздел снимка `specSheets`, вкладка «🏠 Спецификация» (доступ у РОП и менеджера по продажам). Расчёт — в `src/spec.js`, общий модуль: одни и те же числа нужны экрану, печатной форме клиенту, сумме договора и составу работ объекта. Разъедься они — клиент получит одну цену на руки и другую в договоре.
- Вариант выбора — это ПОМЕЧЕННАЯ смета: `optScope` (`room` / `global` / пусто = входит всегда), `optGroup` («Стены»), `optLabel` («МДФ»), `optSurface` (`floor`/`wall`/`ceil` — чем меряется). Отдельной сущности «опция» нет: смета уже знает свои материалы, а вторая копия того же разошлась бы с первой.
- Выбор по комнате хранится **по группе**: `sheet.rooms[roomId][group] = estId`. Не по трём поверхностям — «Стены черновые» и «Стены чистовые» это разные решения об одной стене, в трёх ячейках они бы столкнулись.
- **Раскладка** (`SPEC_POINTS`, `r.pts`) — то, что дизайн-проект рисует значками, а бригада монтирует поштучно: окна, двери, розетки (обычные / влагозащищённые / уличные), выключатели, светильники, споты, тёплый пол, кондиционер, вытяжка, радиатор. Считается ПО ПОМЕЩЕНИЯМ, потому что там же и монтируется, а клиент читает проект по комнатам («в зале шесть розеток и шесть светильников»). Нулевые ключи не храним.
- Смета с `optPoint` берёт количество из раскладки: «Розетка — монтаж» ×15 умножает и материалы, и цену. `optPoint` ортогонален `optScope`: обязательная позиция считается по всему дому, комнатная — по своей комнате. Точек нет — позиции нет: платить за монтаж того, чего не заложили, не за что. Площадь у такой позиции не считается — штуки и квадраты не смешиваем.
- Площади считаются из размеров помещения (`roomArea`): пол = ш × д, потолок равен полу (это одна плоскость, а не отдельный размер), стены = периметр × высота. Количество материала под площадь — `matQtyForArea`: м² как есть, листы и пачки через `packPer` вверх, штучное не трогаем (саморезы от площади не считают).
- Чертёж планировки можно **загрузить прямо в спецификацию** (`obj-doc-upload` → `specs.planUrl`), а размеры внести руками тем же редактором, что у планировок и объектов (`specsEditorHtml`, владелец через `specOwner`). Планировок в базе нет под каждый вид и под каждого клиента — чертёж приносят на встречу. Кнопка «В базу» заводит загруженный план в `dbPlans` копией размеров: иначе он грузится заново каждому клиенту.
- Список планировок в селекте (`specPlanOptions`) показывает ВСЕ, своя категория первой группой. Видов смет уже шесть (апартаменты, глэмпинг…), а категорий у планировок две — жёсткий фильтр оставлял продавца с пустым списком.
- **Спецификация — КОПИЯ планировки, а не ссылка** (`specApplyPlan`). Планировку в базе правят постоянно, а проданное обязано остаться таким, как продали. Смена планировки сбрасывает выбор по комнатам: `id` помещений стали другими, и выбор повис бы в пустоте.
- Наценка ОДНА на спецификацию (`sheet.markup`, по умолчанию `settings.specMarkup`), не по работам, как в КП: продавец должен понимать, что он назвал клиенту, а не собирать сумму из сорока процентов. В печатной форме наценка размазывается по позициям пропорционально, иначе суммы по помещениям не сойдутся с итогом.
- Клиенту печатаем позиции **по ЭТАПАМ** с подытогом каждого: стройка меряется этапами, по ним же идут сроки, приёмка и транши, и предложение должно читаться в том же разрезе. Сводка по помещениям идёт отдельной короткой таблицей в конце — в разрезе этапов она повторяла бы одни и те же комнаты в каждом блоке.
- В каждой позиции печатаем **состав материалов** (название и количество с единицей) — это и есть спецификация, а не КП. Закупочных цен и себестоимости там нет: количество клиенту нужно, наша калькуляция — нет. Формулировка состава одна на экран и на печать (`specMatsText`): разойдись они, в кабинете обещали бы одно, а на бумаге стояло другое.
- `sheetIssues` перечисляет, чего не хватает (нет планировки, не задана высота, не выбран вариант), и продавец видит это ДО клиента. Отказ от предупреждения останавливает создание договора — иначе предупреждение просто текст.
- **Объект создаётся из спецификации, а не из шаблона** (`specBuildStages`): `o.templateId=""`, `o.specId`, работы той же формы, что даёт `_tplEstWork`, поэтому закупка, приёмка, сроки и ревизии работают без единой правки. Раньше объект копировался из фиксированного шаблона, и всё, что клиент выбрал при продаже, до стройки не доезжало.
- Договор из спецификации хранит `c.specId` и сумму `t.price` — через полгода видно, из чего эта сумма собралась. Если объект создан после договора, он привязывается к нему тут же: иначе договор остаётся без стройки, а стройка без денег.

## Вход и защита от перебора

- PIN — четыре цифры, а `/api/login` и `/api/client-login` открыты без авторизации, поэтому в Worker есть сторож `login_guard` (таблица создаётся сама): 5 неудач по личности или 25 по адресу за 15 минут закрывают вход на 15 минут, каждая неудача ещё и тормозится на 400 мс.
- Счёт по ДВУМ ключам: личность (нормализованный телефон / договор) и IP. Порог по адресу выше — бригада на объекте сидит за общим мобильным NAT, и опечатки коллег не должны запирать вход всем.
- Сбой D1 в стороже — **fail-open**: вход продолжает работать. Запереть всю компанию снаружи портала хуже, чем пропустить перебор в момент, когда база и так лежит.
- Ответ на неудачу ОДИН и тот же на «нет такого телефона» и «PIN не тот» (`Неверный телефон или PIN`, у клиента — `Договор не найден или неверный PIN`). Раздельные тексты позволяли перебором узнать, кто работает в компании и кто у неё в клиентах. `PIN не задан` — исключение: это незаконченная настройка, а не перебор, и в счётчик не пишется.
- Успешный вход обнуляет счётчики. PIN пока хранится в снимке открытым (`users[].pin`) — от неадминов вырезается при чтении; переход на хеш потребует решить, как админ сообщает сотруднику забытый PIN.

## Тесты

`npm test` (`tools/run-tests.mjs`) прогоняет ВСЕ наборы `tools/test-*.mjs` — каждый отдельным процессом, потому что панельные наборы держат общий стейт в `node:vm`. Новый файл `tools/test-*.mjs` подхватывается сам, правок в package.json и CI не нужно.

- Общие модули: `test-stage-schedule` — сроки этапов (`src/stages.js`).
- Сквозные: `test-spec` — расчёт спецификации (`src/spec.js`), `test-spec-sheet` — вкладка «Спецификация» целиком: копия планировки, выбор вариантов, печать клиенту, договор и объект из спеки. `test-photo-queue` — офлайн-очередь фото, `test-selection` — выбор клиента и бюджет, `test-tpl-revision` — «в шаблоне изменилось», `test-stock` — склад остатков (перекуп → склад → выдача, без двойного расхода), `test-acceptance` — приёмка этапа и транши, обе половины (панель + ручка Worker'а).
- Панель (`tools/harness/panel-vm.js` — admin.js в `node:vm` с поддельным DOM, стейт синтетический): `test-supply-group` — групповая правка закупки, `test-material-link` — связь с каталогом, `test-mat-change` — заявка на замену, `test-state-sync` — что именно уходит в облако и что держат стражи (`boot({net})` подменяет fetch).
- Worker/бот (моки D1 и fetch, гоняют настоящий `worker.fetch`): `test-login-guard` — вход и перебор PIN, `test-state-api` — версия снимка и скоуп оптимистичной блокировки, `test-botissue`, `test-issue-escalation`, `test-stt`, `test-ogg`.

**CI гоняет их перед выкатом:** в `deploy.yml` есть job `test`, оба деплой-job'а стоят на `needs: test` — упавший тест останавливает выкат целиком. Всё равно гоняйте локально перед пушем в `main`: прогон ~3 с.

## История действий (вкладка «🕘 История»)

- Лог пишет **Worker**, а не панель: `postState` читает снимок «до», `src/audit.js` сравнивает его с пришедшим и записывает разницу в отдельную таблицу D1 `audit_log`. В `admin.js` логирования нет и добавлять не надо — новые действия попадают в историю сами.
- Автор берётся из подписанного токена (`auth.uid`), время — серверное; из панели запись не подделать. Таблица append-only, эндпоинта на правку/удаление нет.
- В снимок лог НЕ кладём (лимит 2 МБ на строку). Разделы без метки в `SECTION_LABELS` не логируются; секретные поля (`pin`, `token`, …) пишутся как `•••`.
- Дёшево за счёт сравнения СЫРЫХ строк JSON по разделам: неизменившееся отсеивается без парсинга. Пишется в `ctx.waitUntil` — сохранение панели не тормозит.
- Правки одного поля в течение 2 минут склеиваются в одну запись (`cnt`), иначе посимвольный ввод давал бы десяток строк.
- `GET /api/audit`: админ видит весь портал, обычный сотрудник — только свои действия (сервер подменяет `uid`), клиент — 403.

## Полевой режим: очередь фото

- Стейт офлайн переживает всё (localStorage-кэш + дожим при уходе), а фото до этого терялось: один `fetch` без сети — и отчёт о работе пропадал с алертом. Файл кладётся в **IndexedDB** (`kubr_uploads`) и досылается сам.
- Прикрепление к работе делает ТА ЖЕ очередь (`photoAttach`), а не загрузка: иначе фото уехало бы в R2, а в объекте его бы не было. Битую ссылку в стейт не пишем — её потом не отличить от настоящей.
- Досылка останавливается на первой сетевой ошибке: связи всё ещё нет, перебирать остальные — жечь батарею. Запускается на `online`, на возврате во вкладку, на старте циклов и раз в минуту, пока очередь не пуста.
- Автор и время берутся из момента СЪЁМКИ, а не отправки. Если работу за это время удалили, элемент из очереди убирается — иначе она копится вечно.
- Хранилище подменяемо (`_uploadStore`), поэтому логика очереди тестируется без браузера (`test-photo-queue`).
